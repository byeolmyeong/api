# 운영 서버를 Ampere A1(2 OCPU · 12GB)로 옮긴다

> 상태: 초안(소유자 승인 전) · 기준 2026-11-20 · 서버 develop `dbd51d6` · 소유자 결정 "서버를 오라클 Always Free Ampere A1 으로 옮긴다" · "그러자, 바꾸자" · "운영만, 스테이징은 지금 VM 그대로"(2026-11-20, 67 세션 경유) · 맡은 곳: 무중단 배포 세션 · 서버 결정 050(042 · 047~ 는 다른 세션 몫)
> **운영을 건드리는 단계(태스크 4 의 운영 쪽 이후)는 소유자 "해" 를 받은 뒤에만 한다.**

## 목표
- 무엇을: 운영 서버(api.byeolmyeong.com)를 E2.1.Micro(1GB · 버스트 CPU)에서 Ampere A1 `VM.Standard.A1.Flex` 2 OCPU · 12GB(arm64)로 옮긴다. 새 VM 은 처음부터 블루 · 그린(결정 046)으로 깐다.
- 왜: 블루 · 그린은 배포 때 JVM 둘이 잠깐 함께 뜬다. 1GB VM 에서는 그동안 VM 전체가 느려진다(아래 "왜 지금" 의 스테이징 실측). 운영은 끊기면 안 된다(소유자).
- 끝나면: 운영 배포(`main` 합치기)가 새 VM 에서 끊김 없이 돌고, 배포 중 응답 시간이 평소와 같다. 옛 운영 VM 은 지운다.

## 왜 지금 (스테이징 실측, 2026-11-20, E2.1.Micro)
| 경우 | 새 JVM 시작 | 0.1초 고리 실패 | 느려짐 |
|---|---|---|---|
| 옛 서버 옆에 블루 띄우기 | 94초 | 0 | 스왑 329MB · 남은 메모리 356MB |
| 자동 배포(생성 1건 동시) | 187초 → `/health` 3분을 넘겨 **바꾸지 않고 실패**(블루가 그대로 받음) | 1(10초 시간 초과) | load 9.7 · `/auth/session` 0.3~1.5초(67 관측) |
| `swap.sh --restart` | 121초 | 1(Caddy 다시 읽기 순간의 연결 끊김) | p99 0.5초 · 최대 9.3초 |
- 평소에도 CPU steal 2~10% · 스왑에서 계속 읽는다(서버 하나 264MB, 남은 메모리 17MB). E2.1.Micro 는 1/8 OCPU 기준에 버스트라, JVM 시작처럼 오래 CPU 를 쓰면 느려진다.
- **스테이징은 이 VM 그대로 남으므로, 스테이징에서 잰 배포 끊김 · 느려짐은 앞으로도 운영보다 나쁘게 나온다.** 스테이징 수치를 운영의 기대치로 읽지 않는다.

## 결정된 전제 (링크만)
- 결정 020(오라클 · 춘천 · Compose 셋 · 백업 · "출시가 가까워질 때 운영 서버를 더 큰 서버로 옮긴다" · 무료 한도 절), 046(블루 · 그린 · `swap.sh`), 017(점검 모드), `docs/deploy.md`.
- 운영 덤프는 운영 VM 밖(개인 컴퓨터 · 스테이징)으로 옮기지 않는다(결정 020 #5). 옛 운영 VM → 새 운영 VM 으로는 VCN 안에서 바로 옮긴다.

## 내 결정 (묻지 않고 고른 기본값)
- **크기 2 OCPU · 12GB 확정**(소유자). 2026년에 Always Free A1 한도가 4 · 24 → 2 · 12 로 줄었다는 보도가 있고(시행일 6/15 · 8/18 로 갈림, 한도를 넘는 인스턴스는 종료된다는 말도 있음), 운영에는 2 · 12 로 충분하다. 4 · 24 는 쓰지 않는다.
- **블루 · 그린을 새 VM 에 바로 깐다**(`docs/deploy.md` (다) "새 VM 에 처음 띄우기"). 옛 운영 VM 은 블루 · 그린으로 옮기지 않는다(그 2~3초 끊김도 없앤다).
- **JVM 힙은 VM 마다 `.env` 로**: compose 의 `-Xmx256m` 고정을 `-Xmx${API_HEAP_MAX:-256m}` 로 바꾸고, 새 운영 `.env` 에 `API_HEAP_MAX=1g`. 스테이징은 그대로 256m. 1g × 2(겹칠 때) + 비힙 + Postgres · Caddy 는 12GB 의 1/4 아래다.
- **DB 는 덤프 · 복원**(지금 8.5MB → 수 초). 아키텍처가 달라 볼륨을 그대로 옮기지 않는다.
- **인증서는 옛 VM 의 `caddy-data` 볼륨을 복사**해 DNS 를 바꾸기 전에 새 Caddy 가 이미 인증서를 갖게 한다(못 하면 DNS 를 바꾼 뒤 Caddy 가 새로 받는다 — 수 초).
- **점검 모드로 쓰기를 멈춘 사이에 마지막 덤프 → 복원 → DNS 를 바꾼다.** 덤프 뒤의 쓰기가 사라지지 않게 하는 가장 단순한 방법이다. 점검 화면이 보이는 시간은 3~5분으로 잡는다(덤프 · 복원 1분 안팎 + 확인 + DNS TTL 60초). 블루 · 그린 첫 전환 때의 "점검 모드 없이" 와는 다르다 — 이번에는 DB 를 옮겨서 쓰기를 멈춰야 한다.
- 과금이 생길 수 있는 것(유료 셰이프 · 무료를 넘는 스토리지 · 로드 밸런서 · 예약 IP 초과)은 쓰지 않는다.

## 범위 밖
- 스테이징 이전(소유자: 그대로 둔다). 스테이징의 느려짐은 남는다.
- DB 복제 · 무점검 이전(논리 복제는 옛 Postgres 를 `wal_level=logical` 로 다시 띄워야 해서 그것도 끊긴다).

## 전역 제약
- 비밀값(`.env` · `db.env` · `backup.env`)은 옛 VM → 새 VM 으로 ssh 파이프로만 옮기고 출력 · 저장하지 않는다.
- 운영 단계는 소유자 "해" 뒤. 단계마다 되돌리는 길을 적는다.

## 태스크

### 1. 소유자 확인(콘솔) · 상태: 대기
- 한도: 오라클 공식 Always Free 문서와 콘솔(Governance → Limits, 춘천)의 `standard-a1-core-count` · `standard-a1-memory-count`. 2026-11-18 조회는 **둘 다 0** 이었다(결정 020) — 0 이면 A1 을 만들 수 없다.
- **종량제(PAYG) 전환이 필요한지 정한다** — 이 계획에서 가장 큰 갈림길:
  - 무료 계정은 A1 한도가 0 이거나 "Out of host capacity" 가 잦다. 종량제는 한도 · 용량 우선순위가 낫다(무료 범위 안이면 0원).
  - **유휴 회수**: 무료 계정은 7일 동안 CPU(95번째 백분위) · 네트워크 · **메모리(A1 만) 사용률이 20% 아래면 회수할 수 있다.** 12GB 에서 우리는 1~2GB 를 쓴다 → 메모리 기준에 걸린다. 종량제 계정은 회수 대상이 아니다. **운영을 무료 계정 A1 에 두면 회수될 위험이 있다.**
  - 전환하면 Billing → Budgets 에 예산 알림(예: 1달러)을 건다(결정 020 (가) 2).
- 스토리지: 부트 볼륨 합 200GB 이하 — 지금 E2.1.Micro 둘(각 약 47GB) + 새 A1(기본 47GB) ≈ 141GB. 옛 운영 VM 을 지우면 ≈ 94GB.
- 개수: 옮기는 동안 E2.1.Micro 2대(한도 2) + A1 2 · 12 가 함께 있다 — 각자 한도 안.
- 검증: 한도 화면 캡처 또는 값, PAYG 여부를 계획의 실행 기록에.

### 2. 결정 050 · compose 힙 · 상태: 대기
- 결정 050 "운영 서버는 Ampere A1 2 OCPU · 12GB(arm64)" — 020 #1 의 운영 셰이프 · "JVM 이 스스로 고른 값" 과 046 #7 의 256m 고정을 대체(스테이징은 그대로). 020 · 046 앞머리 표시.
- compose: `JAVA_TOOL_OPTIONS: -Xmx${API_HEAP_MAX:-256m} -XX:+ExitOnOutOfMemoryError`, `deploy/.env.example` 에 `API_HEAP_MAX`(운영 1g · 스테이징 비움).
- 검증: `docker compose config` 로 두 값(비움 → 256m, 1g) · 스테이징 배포 한 번(값 그대로).

### 3. 새 운영 VM 만들기 · 상태: 대기 (소유자 콘솔, 또는 소유자가 CLI 세션을 열어 주면 Claude)
- Compute → Create instance: 이름 `byeolmyeong-prod-a1`, 셰이프 `VM.Standard.A1.Flex` 2 OCPU · 12GB(**"Always Free-eligible" 표시를 확인**), 이미지 Canonical Ubuntu 24.04 **Minimal aarch64**, 서브넷 `byeolmyeong-public-subnet`, 공인 IPv4 켬, SSH 키 `~/.ssh/byeolmyeong-oci.pub`, 부트 볼륨 기본.
- "Out of host capacity" 면: 몇 시간 뒤 다시(춘천은 가용 영역 하나 · 장애 영역 셋 — 장애 영역을 바꿔 본다). 짧은 간격으로 계속 두드리는 스크립트는 쓰지 않는다(30분 이상 간격). 계속 안 되면 PAYG 전환을 다시 본다.
- 운영 배포용 키를 `restrict` 로 더한다(`docs/deploy.md` (가) 4, 공개 키 `~/.ssh/byeolmyeong-deploy-prod.pub`).

### 4. 새 VM 준비 · 시험 복원 · 상태: 대기 (여기까지는 사용자에게 보이지 않는다)
- `deploy/bootstrap-vm.sh prod`(arm64 에서도 같다 — 아키텍처에 기대는 줄이 없다. 매일 04:00 백업 cron 도 깐다).
- 비밀값: 옛 VM 의 `.env` · `db.env` · `backup.env` 를 새 VM 으로 ssh 파이프(출력 없음), 새 `.env` 에 `API_HEAP_MAX=1g`.
- 인증서: 옛 VM 의 `byeolmyeong_caddy-data` 볼륨을 tar 로 새 VM 볼륨에.
- 파일 · jar: 저장소 `develop` 의 `deploy/` 와 **지금 운영의 jar**(옛 VM `app.jar.good`)를 새 VM 으로 → `./swap.sh --init` → `docker compose up -d postgres caddy`.
- 시험 복원: 옛 VM 에서 지금 덤프(점검 없이) → 새 VM → `./restore.sh <덤프>`(일회용 컨테이너로 행 수) → `./restore.sh <덤프> --into-live` → `./swap.sh <jar>`. 새 VM 의 서버를 `curl --resolve api.byeolmyeong.com:443:<새 IP> https://api.byeolmyeong.com/health` · `/app-config` 로 본다. 덤프 · 복사 · 복원에 걸린 시간을 잰다.
- arm64: 이미지 셋(`eclipse-temurin:21-jre` · `postgres:17.12` · `caddy:2.11.9`)은 `linux/arm64/v8` 이 있다(2026-11-20 확인). jar 에는 네이티브 라이브러리가 없다(같은 날 확인) — 그대로 돈다.
- 되돌리기: 이 태스크는 새 VM 만 만진다. 버리면 끝.

### 5. 전환 · 상태: 대기 (**소유자 "해" 뒤**, 사용자가 적은 시간)
1. 하루 전: Cloudflare 의 `api` A 레코드 TTL 을 60초로(DNS 만, 프록시 끔 그대로).
2. 관리 화면에서 점검 모드를 켠다(옛 VM). 쓰는 중인 생성이 끝날 때까지(`docs/deploy.md` (다) 4 의 질의가 0).
3. 옛 VM: `./backup.sh predeploy`(버킷에도 올라간다) → 그 덤프를 새 VM 으로(VCN 안 사설 주소).
4. 새 VM: `./restore.sh <덤프> --into-live` → `docker compose start api-$(cat active_color)` → `curl --resolve` 로 `/health` · 관리자 로그인 · 앱 설정(점검 켜짐이 복원돼 있어야 맞다).
5. Cloudflare: `api` A 레코드를 새 IP 로. 1~2분 뒤 `dig +short api.byeolmyeong.com` 이 새 IP.
6. 새 서버에서 점검 모드를 끈다(관리 화면 — 브라우저가 새 IP 를 볼 때). 옛 VM 은 점검 켠 채 둔다(늦게 바뀐 사람은 점검 화면을 본다).
7. GitHub 비밀값 `PROD_SSH_HOST` · `PROD_SSH_KNOWN_HOSTS` 를 새 VM 으로. `./backup.sh` 한 번 → 버킷에 오늘 덤프.
- 끊김: 점검 화면 3~5분(2~6). 0.1초 고리와 생성 하나로 잰다.
- 되돌리기: 6 전이면 옛 VM 의 점검을 끄고 DNS 를 되돌린다(잃는 것 없음). 6 뒤면 새 VM 에 쓰인 것이 있으니 같은 절차를 거꾸로(새 → 옛 덤프 · 복원).

### 6. 뒷정리 · 상태: 대기
- 24시간 지켜본다(백업 · 응답 시간 · 메모리). 그 뒤 첫 운영 배포 = `develop` → `main`(S⑧ · S11) — 끊김 없는지 0.1초 고리로.
- 옛 운영 VM: 멈춰 7일 두었다가 Terminate("Permanently delete the attached boot volume" 체크). VM 안의 옛 덤프도 같이 지워진다(버킷은 30일 남는다).
- 문서: `docs/deploy.md` "한눈에"(운영 VM 이름 · 셰이프), (가) 4 의 셰이프 · 이미지, 결정 020 무료 한도 절의 A1 값(확인한 날짜와 함께). TTL 은 다시 자동으로.

## 검증 (전체 완료 판정)
- 전환: 점검 화면 시간이 계획 안(≤ 6분), 전환 뒤 첫 운영 배포에서 0.1초 고리 실패 0 · 응답 p99 가 평소와 같음 · 그 사이 시작한 생성이 DONE.
- 백업: 새 VM 의 매일 백업이 버킷에 올라감(다음 날 아침).
- 옛 운영 VM 을 지운 뒤 부트 볼륨 합 · 인스턴스 수가 무료 한도 안.

## 리뷰 초점
- 유휴 회수(무료 계정이면 메모리 20% 기준에 걸림) — PAYG 를 하지 않기로 하면 이 위험을 소유자가 알고 정한다.
- 비밀값 · 운영 덤프가 VM 밖에 남지 않는지(파이프만, 파일 없음).
- 전환 6 의 순서(점검을 끄기 전에 DNS 가 새 IP 인지).

## 위험 · 되돌리기
- 한도 0 · 용량 없음 → 만들지 못하면 이 계획은 멈추고 운영은 지금 VM(블루 · 그린으로 옮기기 전, 배포는 멈춘 채)이다. 그때는 지금 VM 을 블루 · 그린으로 옮기는 원래 절차(끊김 2~3초)로 간다.
- 한도가 공지 없이 또 줄면(보도) 인스턴스가 종료될 수 있다 → 매일 백업(버킷 30일)으로 다른 곳에 복원. 결정 020 의 재검토 조건(유료 VPS)으로.

## 실행 기록

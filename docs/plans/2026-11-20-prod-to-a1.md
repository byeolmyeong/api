# 운영 서버를 Ampere A1(2 OCPU · 12GB)로 옮긴다

> 상태: 승인(소유자 2026-11-20 "종량제 전환 OK, 전환 때 점검 화면 3~5분 OK") · 기준 2026-11-20 · 서버 develop `dbd51d6` · 소유자 결정 "서버를 오라클 Always Free Ampere A1 으로 옮긴다" · "그러자, 바꾸자" · "운영만, 스테이징은 지금 VM 그대로"(2026-11-20, 67 세션 경유) · 맡은 곳: 무중단 배포 세션 · 서버 결정 050(042 · 047~ 는 다른 세션 몫) · 운영을 바꾸는 단계(인스턴스 만들기 · DNS · 점검)는 실행할 때 다시 "해" 를 받는다
> **운영을 건드리는 단계(태스크 4 의 운영 쪽 이후)는 소유자 "해" 를 받은 뒤에만 한다.**

## 목표
- 무엇을: 운영 서버(api.byeolmyeong.com)를 E2.1.Micro(1GB · 버스트 CPU)에서 Ampere A1 `VM.Standard.A1.Flex` 2 OCPU · 12GB(arm64)로 옮긴다. 새 VM 은 처음부터 블루 · 그린(결정 046)으로 깐다.
- 왜: 블루 · 그린은 배포 때 JVM 둘이 잠깐 함께 뜬다. 1GB VM 에서는 그동안 VM 전체가 느려진다(아래 "왜 지금" 의 스테이징 실측). 운영은 끊기면 안 된다(소유자).
- 끝나면: 운영 배포(`main` 합치기)가 새 VM 에서 끊김 없이 돌고, 배포 중 응답 시간이 평소와 같다. 옛 운영 VM 은 지운다.

## 왜 지금 (스테이징 실측, 2026-11-20, E2.1.Micro)
| 경우 | 새 JVM 시작 | 0.1초 고리 실패 | 느려짐 |
|---|---|---|---|
| 옛 서버 옆에 블루 띄우기 | 94초 | 0 | 스왑 329MB · 남은 메모리 356MB |
| 자동 배포(생성 1건 동시) | 187초 → `/health` 3분을 넘겨 **바꾸지 않고 실패**(블루가 그대로 받음) | 1(10초 시간 초과) | load 9.7 · `/auth/session` 0.3~1.5초(67 관측) |
| `swap.sh --restart` | 121초 | 1(Caddy 다시 읽기 순간의 연결 끊김) | p99 0.5초 · 최대 9.3초 |
- 평소에도 CPU steal 2~10% · 스왑에서 계속 읽는다(서버 하나 264MB, 남은 메모리 17MB). E2.1.Micro 는 1/8 OCPU 기준에 버스트라, JVM 시작처럼 오래 CPU 를 쓰면 느려진다.
- **스테이징은 이 VM 그대로 남으므로, 스테이징에서 잰 배포 끊김 · 느려짐은 앞으로도 운영보다 나쁘게 나온다.** 스테이징 수치를 운영의 기대치로 읽지 않는다.

## 결정된 전제 (링크만)
- 결정 020(오라클 · 춘천 · Compose 셋 · 백업 · "출시가 가까워질 때 운영 서버를 더 큰 서버로 옮긴다" · 무료 한도 절), 046(블루 · 그린 · `swap.sh`), 017(점검 모드), `docs/deploy.md`.
- 운영 덤프는 운영 VM 밖(개인 컴퓨터 · 스테이징)으로 옮기지 않는다(결정 020 #5). 옛 운영 VM → 새 운영 VM 으로는 VCN 안에서 바로 옮긴다.

## 내 결정 (묻지 않고 고른 기본값)
- **크기 2 OCPU · 12GB 확정**(소유자). 2026년에 Always Free A1 한도가 4 · 24 → 2 · 12 로 줄었다는 보도가 있고(시행일 6/15 · 8/18 로 갈림, 한도를 넘는 인스턴스는 종료된다는 말도 있음), 운영에는 2 · 12 로 충분하다. 4 · 24 는 쓰지 않는다.
- **블루 · 그린을 새 VM 에 바로 깐다**(`docs/deploy.md` (다) "새 VM 에 처음 띄우기"). 옛 운영 VM 은 블루 · 그린으로 옮기지 않는다(그 2~3초 끊김도 없앤다).
- **JVM 힙은 VM 마다 `.env` 로**: compose 의 `-Xmx256m` 고정을 `-Xmx${API_HEAP_MAX:-256m}` 로 바꾸고, 새 운영 `.env` 에 `API_HEAP_MAX=1g`. 스테이징은 그대로 256m. 1g × 2(겹칠 때) + 비힙 + Postgres · Caddy 는 12GB 의 1/4 아래다.
- **DB 는 덤프 · 복원**(지금 8.5MB → 수 초). 아키텍처가 달라 볼륨을 그대로 옮기지 않는다.
- **인증서는 옛 VM 의 `caddy-data` 볼륨을 복사**해 DNS 를 바꾸기 전에 새 Caddy 가 이미 인증서를 갖게 한다(못 하면 DNS 를 바꾼 뒤 Caddy 가 새로 받는다 — 수 초).
- **점검 모드로 쓰기를 멈춘 사이에 마지막 덤프 → 복원 → DNS 를 바꾼다.** 덤프 뒤의 쓰기가 사라지지 않게 하는 가장 단순한 방법이다. 점검 화면이 보이는 시간은 3~5분으로 잡는다(덤프 · 복원 1분 안팎 + 확인 + DNS TTL 60초). 블루 · 그린 첫 전환 때의 "점검 모드 없이" 와는 다르다 — 이번에는 DB 를 옮겨서 쓰기를 멈춰야 한다.
- 과금이 생길 수 있는 것(유료 셰이프 · 무료를 넘는 스토리지 · 로드 밸런서 · 예약 IP 초과)은 쓰지 않는다.

## 범위 밖
- 스테이징 이전(소유자: 그대로 둔다). 스테이징의 느려짐은 남는다.
- DB 복제 · 무점검 이전(논리 복제는 옛 Postgres 를 `wal_level=logical` 로 다시 띄워야 해서 그것도 끊긴다).

## 전역 제약
- 비밀값(`.env` · `db.env` · `backup.env`)은 옛 VM → 새 VM 으로 ssh 파이프로만 옮기고 출력 · 저장하지 않는다.
- 운영 단계는 소유자 "해" 뒤. 단계마다 되돌리는 길을 적는다.

## A1 을 기다리는 동안: 지금 운영 VM 을 블루 · 그린으로 (소유자 ② — 2026-11-20)
A1 용량이 없어(실행 기록) 운영 배포가 멈춰 있으므로, 지금 운영 VM(E2.1.Micro)을 먼저 블루 · 그린으로 옮긴다. 점검 모드 없이, Caddy 를 다시 만드는 순간의 끊김(스테이징 3.2초)을 받아들인다(소유자). **실행은 아래 표를 소유자에게 보이고 "해" 를 받은 뒤.** A1 이 생기면 이 계획의 태스크 3~6 으로 그대로 옮긴다(새 VM 도 블루 · 그린).

- **운영도 지금은 같은 E2.1.Micro 라 배포 때 1.5~3분 느려지는 것은 스테이징과 비슷하다.** A1 로 옮긴 뒤에는 스테이징만 이렇게 남는다.

### 운영 힙 — 256m 그대로(`API_HEAP_MAX` 를 두지 않는다)
| 힙 상한 | 한 JVM 의 RSS(실측 · 추정) | 둘이 겹칠 때 | 판단 |
|---|---|---|---|
| 192m | 약 170~230MB(추정) | 조금 낫다 | GC 가 잦아 CPU 를 더 쓰고, 생성이 몰리면 메모리 부족으로 죽을 수 있다(`ExitOnOutOfMemoryError` → 다시 뜸) |
| **256m(지금)** | 202~264MB(스테이징) · 214MB(운영) | 남은 메모리 10~30MB · 스왑 330~430MB | 지금까지 운영이 이 값으로 돈다 — 그대로 둔다 |
| 384m | 최대 +128MB | 둘이 겹치면 +256MB 더 스왑 | 더 느려진다 |
| 512m | 최대 +256MB | +512MB 더 스왑 | 1GB VM 에서는 쓰지 않는다 |
- 384~512m 은 지금(256m)보다 **올리는** 값이라 겹칠 때 더 나빠진다. 1GB 에서 병목은 CPU(1/8 OCPU 기준 + 버스트)와 스왑이다. 힙으로는 풀리지 않는다 — 그래서 A1(결정 050).

### 절차 (`docs/deploy.md` (다) "블루 · 그린으로 처음 옮겨 가기", 점검 모드 없이)
1. (맥, `develop`) compose.yaml · swap.sh · restore.sh 만 올린다(Caddyfile 은 5 직전). 운영 `.env` 에 `API_HEAP_MAX` 를 넣지 않는다(256m).
2. 지금 jar(`app.jar` = `app.jar.good`)로 블루를 옛 서버 옆에 띄우고 Caddy 안에서 `/health` 200 까지(스테이징 94초).
3. `./swap.sh --init` · `docker compose pull caddy`.
4. (점검 모드 없음) 쓰는 중인 생성이 있으면 끝날 때까지 기다린다(같은 질의가 0) — 옛 jar 는 끌 때 생성을 기다리지 않는다.
5. Caddyfile 을 올리고 `docker compose up -d --no-deps caddy` — **여기서 약 3초 끊긴다.** VM 밖(맥)에서 `/health` 200 · 관리 API 에 `api-blue:8080`. (VM 안에서 자기 공인 주소로 curl 하지 않는다 — 닿지 않는다.)
6. `echo blue > active_color && cp app-blue.jar app.jar.good`
7. 옛 `api` 컨테이너를 내리고 지운다 · `rm -f app.jar app.jar.new`.
8. 그 뒤 첫 운영 배포 = `develop` → `main`(S⑧ · S11 · S⑪ #37 포함). 워크플로가 swap 으로 올린다.
- 측정: 맥에서 운영 주소로 0.1초 고리를 2~8 내내, 그리고 8 의 배포 내내 켜 둔다. 표: 요청 · 실패(건수 · 초) · p99 · 최대.
- 되돌리기: 5 뒤에 문제가 있고 7 전이면 — 옛 Caddyfile(`reverse_proxy api:8080`)을 다시 올리고 `docker compose exec -T caddy caddy reload --config /etc/caddy/Caddyfile`(옛 `api` 가 아직 떠 있다, 다시 만들지 않아 끊기지 않는다). 7 뒤면 `./swap.sh <이전 jar>`(끊김 없이).

## 태스크

### 1. 소유자 확인 · 종량제(콘솔) · 상태: 완료
- 한도: 오라클 공식 Always Free 문서와 콘솔(Governance → Limits, 춘천)의 `standard-a1-core-count` · `standard-a1-memory-count`. 2026-11-18 조회는 **둘 다 0** 이었다(결정 020) — 0 이면 A1 을 만들 수 없다.
- **종량제(PAYG)로 올린다**(소유자 OK, 결정 050 의 3) — 까닭:
  - 무료 계정은 A1 한도가 0 이거나 "Out of host capacity" 가 잦다. 종량제는 한도 · 용량 우선순위가 낫다(무료 범위 안이면 0원).
  - **유휴 회수**: 무료 계정은 7일 동안 CPU(95번째 백분위) · 네트워크 · **메모리(A1 만) 사용률이 20% 아래면 회수할 수 있다.** 12GB 에서 우리는 1~2GB 를 쓴다 → 메모리 기준에 걸린다. 종량제 계정은 회수 대상이 아니다. **운영을 무료 계정 A1 에 두면 회수될 위험이 있다.**
  - 전환하면 Billing → Budgets 에 예산 알림(예: 1달러)을 건다(결정 020 (가) 2).
- 스토리지: 부트 볼륨 합 200GB 이하 — 지금 E2.1.Micro 둘(각 약 47GB) + 새 A1(기본 47GB) ≈ 141GB. 옛 운영 VM 을 지우면 ≈ 94GB.
- 개수: 옮기는 동안 E2.1.Micro 2대(한도 2) + A1 2 · 12 가 함께 있다 — 각자 한도 안.
- 검증: 한도 화면 캡처 또는 값, PAYG 여부를 계획의 실행 기록에.

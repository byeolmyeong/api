# 023. 생성 기능의 계정별 한도는 모델을 실제로 부르는 요청만 센다

> 상태: 활성 · 결정일 2026-11-19(소유자, 독립 리뷰의 지적에 "모델을 부른 것만 세기") · 결정 022 의 3번 중 "저장본을 돌려준 요청도 센다"를 대체한다(숫자·경로·응답은 그대로) · 계획 docs/plans/2026-11-19-pre-deploy-hardening.md

## 맥락
- 결정 022 는 생성 경로 다섯 곳(`POST /readings`·`POST /reports`·`POST /synastry/{id}/report`·`POST /directions`·`POST /synastry/direct`)의 POST 를 한 계정이 합쳐 분당 5번·시간당 30번까지로 하고, 저장본을 돌려준 요청도 셌다.
- 독립 리뷰가 앱의 호출을 보고 짚었다: 앱은 리포트 화면을 열 때마다 `POST /directions`(미래)를 부르고, 출생 정보가 없으면 POST 를 두 번 보낸다. 요약·리포트·방향성을 오가며 보는 사용자는 모델을 한 번도 더 부르지 않아도 한 시간에 30번을 넘겨 "횟수 한도"를 볼 수 있다.
- 한도의 목적은 모델 비용의 남용을 막는 것이다(결정 022 근거). 저장본은 비용이 들지 않는다.

## 결정
1. **세는 것은 "모델 생성을 시작하는 요청"이다.** 저장본을 돌려주는 요청, 출생 정보가 없어 404 인 요청, 이미 쓰는 중인 리포트에 다시 온 요청은 세지 않는다.
2. **세는 자리**: 각 서비스가 저장본이 없음을 확인하고 생성을 시작하기 직전에 한 번 센다(재시도 세 번은 한 번으로). 리포트·궁합 리포트는 여러 영역을 만들어도 요청 하나를 한 번으로 센다.
   - 요약 해석: 진행 중 생성 표시를 잡은 요청만 센다. 기다리던 요청은 세지 않고 앞 요청과 같은 결과(429 포함)를 받는다.
   - 리포트·궁합 리포트: 자리를 잡은(claim) 뒤에 센다. 한도를 넘으면 그 자리를 실패로 돌려(`fail`) 쓰는 중으로 남지 않게 하고 429 를 준다. 다음 요청은 다시 자리를 잡을 수 있다.
   - 직접 입력 궁합: 저장본이 없어 부를 때마다 센다(결정 022 와 같다).
3. **숫자·응답은 결정 022 그대로**: 분당 5번·시간당 30번(설정 `byeolmyeong.rate-limit.generation-per-minute`·`generation-per-hour`), 넘으면 429 `{"error":"RATE_LIMITED"}`. 서버 메모리에서 센다(서버 한 대).
4. 세는 일은 요청 인터셉터가 아니라 서비스가 부르는 `web.GenerationQuota` 한 곳에서 한다(인터셉터는 저장본이 있는지 모른다).

## 근거
- 비용이 드는 일만 센다: 평소 사용자는 저장본을 다시 받으므로 한도를 볼 일이 거의 없고, 남용(새 차트로 계속 생성)은 그대로 막힌다.
- 서비스가 이미 "저장본이 없다"를 아는 자리에서 세므로 저장본 규칙을 두 곳에 복제하지 않는다.

## 대안
- 숫자만 올리기(분당 10·시간당 60) — 고칠 것이 적지만 저장본도 계속 세서 같은 문제가 숫자만 바뀌어 남는다.
- 그대로 두고 출시 뒤 숫자를 보고 바꾸기 — 출시 초기 사용자가 이유 없이 "횟수 한도"를 볼 수 있다.
- 요청이 끝난 뒤 생성했으면 세는 인터셉터(넘었으면 다음 요청을 모두 거절) — 한도에 닿은 사용자는 저장본도 못 받는다.

## 결과·재검토 조건
- 한도를 넘은 리포트 요청의 행은 FAILED 로 남는다. 앱은 POST 의 429 로 한도를 안내하고, 다음 요청이 다시 시작한다.
- 같은 계정의 동시 요청이 겹치면 생성 직전 확인이라 한두 번 더 셀 수 있다(남용 방지에는 문제없다).
- 서버가 둘 이상이 되면 결정 022 처럼 공유 저장소로 옮긴다.

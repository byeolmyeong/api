# 013. 문의는 서버에 저장만 한다 (관리 화면·메일 발송 없음, 계정별 시간당 제한)

> 상태: 활성 · 결정일 2026-11-12(소유자) · docs/architecture.md 의 API 계약·데이터·요청 속도 제한 절에 `POST /inquiries` 를 더한다 · 번호 011·012 는 같은 날 다른 작업 브랜치가 쓰고 있어 013 으로 잡았다.
> 2026-11-20: 종류(새 BUG · IDEA · ACCOUNT · ETC) · 답장 이메일(받지 않음) · 앱 버전(문의 때 앱 헤더를 적어 둔다) · 사용자가 읽는 경로(내 문의 목록 · 한 건) · 글 길이(10~1000자, 옛 앱은 2000자)는 결정 039 가 바꿨다(이 결정의 나머지는 그대로).

## 맥락
- 앱의 설정 화면은 연락처 이메일을 보여 주는 대신 "문의하기" 입력 화면을 둔다(소유자 결정 2026-11-12).
- 문의를 받을 곳이 서버에 없다. 메일 발송 경로도, 관리 화면도 없다.
- 계정 삭제는 "모두 지운다" 고 약속한다. 문의 글과 답장 받을 이메일도 그 사람의 것이다.
- 지금의 요청 속도 제한은 주소(IP)별 분당 셋뿐이다(`web/RateLimitConfig.kt`). 계정별 제한은 배포 전까지 미뤄져 있다(계획 "배포 전 확인" 1번).

## 결정
1. `POST /inquiries`(세션 필요)로 문의를 받아 `inquiries` 테이블에 넣는다. 저장하는 것은 소유자·종류(`ACCOUNT`·`READING`·`SYNASTRY`·`BUG`·`OTHER`)·글·답장 받을 이메일(없을 수 있다)·만든 때뿐이다. 기기 정보·주소(IP)·앱 버전은 받지도 저장하지도 않는다.
2. **관리 화면도 메일 발송도 만들지 않는다.** 지금은 소유자가 테이블을 직접 읽는다:
   ```sql
   select created_at, category, reply_email, body, id, owner_id from inquiries order by created_at desc;
   ```
   관리 화면과 새 문의의 메일 알림은 나중 일이다(이 결정의 범위 밖). 답장은 소유자가 `reply_email` 로 직접 보낸다. 이메일을 남기지 않은 문의에는 답할 길이 없다 — 앱이 입력 화면에서 그렇게 알린다.
3. 사용자가 자기 문의를 다시 보는 경로(`GET`·목록)는 없다.
4. 소유자는 세션에서만 얻는다. `owner_id` 는 `accounts` 를 가리키고 계정을 지우면 문의도 함께 지워진다(`on delete cascade`).
5. 검증은 서버가 한다: 글은 앞뒤 공백을 뗀 10~2000자(글자 수는 유니코드 코드 포인트로 센다 — 한글 한 글자가 1), 이메일은 없어도 되고(키 없음·`null`·빈 글·공백뿐인 글 모두 "없음") 있으면 앞뒤 공백을 뗀 254자 이하에 모양만 본다(`@` 하나, 앞부분이 비지 않음, 뒷부분에 점, 공백 없음). 실제로 있는 주소인지는 확인하지 않는다(DNS·확인 메일 없음).
6. 계정별 제한: 한 계정이 한 시간에 5건까지(`byeolmyeong.rate-limit.inquiries-per-hour`), 넘으면 429 `RATE_LIMITED`. 이미 있는 `web.RateLimiter`(고정 창, 서버 메모리)를 소유자 id 를 키로 `inquiry` 안에서 쓴다. 검증을 통과한 문의만 센다(틀린 요청은 저장도 모델 호출도 없어 세지 않는다). **다른 엔드포인트에는 계정별 제한을 걸지 않는다** — 그쪽은 소유자가 미뤘다(계획 "배포 전 확인" 1번).
7. 문의 글과 답장 이메일은 로그·예외 메시지·오류 응답에 넣지 않는다. 로그에는 이벤트 이름과 종류 코드만 남긴다.

## 버린 대안
- 메일로 바로 보낸다(저장 없이) — 발송 경로가 아직 없고(외부 시스템 표의 "[확인 필요]"), 발송이 실패하면 문의가 사라진다.
- 주소(IP)별 제한을 그대로 쓴다 — 세션이 있는 엔드포인트라 계정이 더 정확한 키이고, 같은 공유기 뒤의 여러 사람이 서로를 막는다.
- 계정별 제한을 인터셉터로 만들어 `web` 에 둔다 — `web` 은 `auth` 를 모른다. 한 곳에서만 쓰는 장치를 공통으로 올리지 않는다. 다른 엔드포인트에 계정별 제한을 걸 때 다시 본다.
- 종류·글 길이를 DB 의 check 제약으로도 건다 — 종류를 늘릴 때마다 마이그레이션이 필요하다. 다른 테이블(`directions.topic`)처럼 서버 코드가 단일 출처다.

## 영향
- 앱: 설정의 "문의하기" 화면이 `POST /inquiries` 를 부른다. 계약은 docs/architecture.md.
- 서버: 새 기능 패키지 `inquiry`(다른 기능 패키지를 모른다), `V11__inquiries.sql`(V10 은 같은 때의 다른 작업 브랜치가 쓴다).
- 제한은 서버 메모리의 고정 창이다: 서버가 다시 뜨면 세던 수가 사라지고, 창의 경계 앞뒤로는 잠깐 한도의 두 배까지 들어올 수 있다. 서버가 여러 대가 되면 다시 본다(`web.RateLimiter` 의 주석과 같다).
- 개인정보: 답장 이메일은 이 서버가 저장하는 첫 연락처다(`accounts` 는 이메일을 받지 않는다). 개인정보 처리방침에 "문의 글과 답장 받을 이메일을 저장하고 계정 삭제 때 지운다" 가 들어가야 한다 — [확인 필요] 소유자.

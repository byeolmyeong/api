# 022. 배포 환경 이름으로 운영의 개발용 로그인을 막고, 생성 기능은 계정별로 속도를 제한한다

> 상태: 활성 · 결정일 2026-11-19(소유자 "다 해"·"승인", 기본값은 Claude 가 정함) · 계획 docs/plans/2026-11-19-pre-deploy-hardening.md

## 맥락
- 개발용 로그인(결정 005)은 켜지면 누구나 같은 계정으로 들어온다. 지금까지 막는 장치는 "설정을 켜지 않으면 404" 라는 기본값뿐이었다(배포 전 확인 2).
- 스테이징은 개발용 로그인을 켜고 운영과 같은 Anthropic 키를 쓴다(결정 020 #6). 주소를 아는 누구나 글 생성을 부를 수 있고, 지금 생성 기능에는 계정별 제한이 없다(배포 전 확인 1). 같은 계정이 요약 해석을 동시에 두 번 부르면 모델도 두 번 불린다.
- 결정 003 은 "기능 횟수 제한은 없다" 고 정했다. 아래 제한은 사용량을 나누는 것이 아니라 짧은 시간의 남용을 막는 속도 제한이다.

## 결정
1. **배포 환경 이름**: 환경 변수 `DEPLOY_ENV`(설정 `byeolmyeong.deploy-env`), 값은 `local`·`staging`·`prod`. **비어 있거나 없으면 `prod` 로 본다** — VM 에서 빠뜨려도 위험한 쪽으로 열리지 않는다. 로컬 개발은 `.env` 에 `local`, 스테이징·운영 VM 은 각자 값을 적는다.
2. **운영 안전장치**: 개발용 로그인(`byeolmyeong.auth.dev-enabled=true`)은 환경이 `local`·`staging` 일 때만 켤 수 있다. 그 밖에서 켜져 있으면 **서버가 시작하지 않는다**(이유를 `event=startup_refused` 한 줄로 남긴다). 404 로 숨기면 켜진 채 운영에 떠도 아무도 모르지만, 시작 실패는 배포의 상태 확인(/health)에서 바로 드러나고 마지막 정상 jar 로 돌아간다.
3. **생성 기능의 계정별 속도 제한**: 모델을 부르는 `POST /readings`·`POST /reports`·`POST /synastry/{id}/report`·`POST /directions`·`POST /synastry/direct` 를 한 계정이 **합쳐서 분당 5번, 시간당 30번**까지(설정 `byeolmyeong.rate-limit.generation-per-minute`·`generation-per-hour`). 넘으면 429 `RATE_LIMITED`. 저장본을 돌려준 요청도 센다(단순하고 예측할 수 있다). 기존 주소별 제한은 그대로다. 서버 메모리에서 센다(서버 한 대, 결정 020).
4. **요약 해석의 동시 요청**: 같은 계정·같은 차트·같은 종류의 생성이 진행 중이면 뒤의 요청은 그 결과를 기다려 같은 것을 받는다. 새 응답 코드를 만들지 않아 앱 계약은 그대로다.

## 근거
- 기본값을 `prod` 로 두면 실수의 결과가 "개발용 로그인이 안 켜짐" 이다. 반대로 두면 실수의 결과가 "운영에서 누구나 로그인" 이다.
- 숫자: 보통 사용자는 생성 결과를 저장본으로 다시 받으므로 분당 5번·시간당 30번에 한참 못 미친다. 스테이징에서 같은 키로 비용을 일으키는 속도는 크게 줄인다.

## 대안
- 운영에서는 404 로만 숨기기(지금까지): 켜진 채 떠도 드러나지 않는다.
- Spring 프로필(`spring.profiles.active`)로 환경 구분: 프로필은 설정 묶음을 바꾸는 용도라 "이 값이 비면 운영" 같은 안전한 기본값을 두기 어렵다.
- 주소(IP)별 생성 제한: 같은 계정이 여러 곳에서 부르면 못 막고, 같은 곳의 다른 사람을 막는다.
- 겹친 요청에 409: 앱이 새 코드를 다뤄야 한다.

## 결과·재검토 조건
- 로컬 `.env` 에 `DEPLOY_ENV=local` 을 적지 않으면 개발용 로그인을 켠 로컬 서버가 시작하지 않는다(루트 `.env.example` 에 적는다).
- 서버가 여러 대가 되면 계정별 제한을 함께 세는 저장소(예: DB·Redis)로 옮긴다.
- 정상 사용자가 429 를 본다는 보고가 있으면 숫자를 올린다.

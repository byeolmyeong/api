# 046. 배포 · 설정 바꾸기는 블루 · 그린으로 끊김 없이 한다

> 상태: 활성 · 결정일 2026-11-20(소유자 "운영서버는 끊기면 안 되는데 무중단 배포해야 해", 기본값은 Claude 가 정함) · 계획 docs/plans/2026-11-20-zero-downtime-deploy.md · 결정 020 의 4번 "바꿔 띄우기" 와 되돌리기 방식을 대체한다(020 의 나머지는 그대로다) · 절차는 docs/deploy.md

## 맥락
- 지금 배포는 서버 컨테이너를 내리고 새로 띄운다(`up -d --force-recreate api`). 1GB · 1 OCPU VM 에서 JVM 이 뜨는 30~60초 동안 Caddy 가 502 를 준다. 운영 `.env` 를 바꿀 때도 같다.
- 같은 배포가 `docker compose pull` + `up -d` 로 Postgres · Caddy 의 새 패치도 받아 다시 만든다. DB 가 다시 뜨면 전부 끊긴다.
- 뒤에서 쓰는 생성(리포트 · 나 탭 · 궁합, 앞으로 시기)은 서버 메모리의 일감이다. 서버가 꺼지면 그 행의 살아 있다는 표시(박동)가 멈추고 2분 뒤 "멈춘 생성(FAILED)" 으로 보인다.
- VM 은 하나다(결정 020). 2026-11-20 운영 측정: 서버 214MiB · Postgres 44MiB · Caddy 17MiB, 남는 메모리 약 460MiB + 스왑 2GB.

## 결정
1. **블루 · 그린**: 서버 컨테이너를 `api-blue` · `api-green` 둘로 두고 늘 하나만 요청을 받는다. jar 는 색마다 `app-blue.jar` · `app-green.jar`. 지금 받는 색은 VM 의 `active_color` 파일에 적는다.
2. **바꾸는 순서**(`deploy/swap.sh`): 새 jar 를 쉬는 색에 넣고 띄운다 → Caddy 컨테이너 안에서 그 색의 `/health` 가 200 이 될 때까지(최대 3분) 기다린다 → 받는 쪽을 바꾼다 → 5초 뒤 옛 색을 차분하게 내린다 → `active_color` 와 지금 jar(`app.jar.good`) · 그 앞 jar(`app.jar.prev`)를 적는다. 새 색이 3분 안에 살아나지 않거나 받는 쪽 바꾸기가 실패하면 새 색을 내리고 실패로 끝낸다 — 받는 쪽은 옛 색 그대로라 되돌릴 것이 없다. **받는 쪽을 바꾸기 전에 옛 색을 내리지 않는다.**
   - `.env` 만 바꿨을 때는 `swap.sh --restart`(지금 jar 를 쉬는 색으로 다시 띄운다). 바로 앞 버전으로 되돌리기는 `swap.sh app.jar.prev`, 더 이전은 배포 수동 실행 — 둘 다 끊김 없다. `app.jar.prev` 는 받는 쪽 jar 가 바뀔 때만 밀려난다(`--restart` · 실패한 배포는 건드리지 않는다).
3. **받는 쪽 바꾸기 = Caddy 설정 다시 읽기**: Caddyfile 은 받는 쪽을 `upstream.caddy` 한 파일에서 가져온다(`import`). 바꿀 때는 그 파일을 고쳐 쓰고 `caddy reload` 한다. 다시 읽기는 연결을 끊지 않고, 받던 요청은 옛 색에서 끝난다. 다시 읽기가 실패하면 Caddy 는 옛 설정을 그대로 쓴다. 바꾼 뒤에는 Caddy 가 실제로 새 색을 쓰는지 관리 API(`/config/`)로 확인한다.
4. **옛 색 내리기 = 차분한 종료**: `server.shutdown=graceful` · `spring.lifecycle.timeout-per-shutdown-phase=120s` — 새 요청은 그만 받고 받던 요청은 끝낸다. 120초는 모델 호출 한 번의 제한 시간이다(요약 해석 · 직접 입력 궁합 · 방향성은 요청 안에서 모델을 부른다). 그 다음 생성 일꾼이 맡은 일을 줄에서 기다리는 것까지 끝까지 쓴다(최대 180초, `byeolmyeong.report.shutdown-wait-seconds`). 기다리는 동안에도 박동을 계속 적어, 새 서버가 그 생성을 멈춘 것으로 보고 가로채지 않는다. 생성을 끊고 다시 시작하게 만들지 않는다. Compose `stop_grace_period: 320s`(120 + 180 + 여유).
   - 받던 요청이 120초를 넘기면(모델이 틀린 답을 줘 다시 부르는 중 등) 끊긴다. 180초 안에 못 끝낸 생성은 서버가 꺼지며 멈추고, 지금처럼 2분 뒤 FAILED 로 보여 사람이 다시 만든다.
5. **두 서버가 잠깐 함께 뜬다**: 새 색이 뜨는 동안과 옛 색이 일을 끝내는 동안(보통 1분 안팎, 최대 약 8분 — 뜨기 3분 + 5초 + 내리기 320초) 두 JVM 이 같은 DB 를 쓴다.
   - **마이그레이션은 옛 jar 를 깨지 않게 쓴다**: 열 · 표를 지우거나 이름을 바꾸는 일, 기존 열에 NOT NULL 을 더하는 일은 두 번의 배포로 나눈다(먼저 새 jar 가 옛 것을 안 쓰게 → 다음 배포에서 지운다). 새 열은 NULL 허용이거나 기본값을 둔다. PR 리뷰에서 본다.
   - **두 번 돌면 안 되는 `@Scheduled` 는 DB 잠금(`pg_try_advisory_lock`)으로 하나만 돌게 한다**(오늘의 하늘 미리 만들기 · 푸시 보내기 같은 것). 박동처럼 서버마다 제 것만 하는 일은 그대로 둔다. 2026-11-20 develop 에는 박동 셋뿐이다.
   - 주소별 요청 제한 · 관리자 로그인 제한 · 생성 한도처럼 서버 메모리에서 세는 것은 바꿀 때 비워진다(지금도 재시작 때 비워진다 — 그대로 둔다).
6. **앱 배포는 서버 컨테이너만 만진다**: Postgres · Caddy 이미지는 패치까지 태그를 고정하고 배포 때 받지도 다시 만들지도 않는다(swap.sh 는 `--no-deps` 로 서버 색만 띄운다). 둘의 업데이트는 따로, 점검 모드(결정 017)를 켜고 한다. 서버 이미지(`eclipse-temurin:21-jre`)는 배포 때 받는다 — 쉬는 색만 새로 만들어지므로 끊기지 않는다.
7. **JVM 메모리 상한**: `JAVA_TOOL_OPTIONS=-Xmx256m -XX:+ExitOnOutOfMemoryError`. 256MB 는 1GB VM 에서 JVM 이 스스로 고르던 값(결정 020 #1)과 같다 — 지금 동작은 그대로 두고, 두 JVM 이 겹쳐도 더 커지지 않게 못 박는다. 메모리가 모자라 죽으면 다시 뜬다(`restart: unless-stopped`).
8. **스테이징도 같은 방식**이다. 운영 전에 스테이징에서 늘 한 번 해 본다.
9. **처음 한 번 옮겨 가기**(`api` → `api-blue`)는 Caddy 컨테이너를 새 마운트로 다시 만들어야 해서 한 번 끊긴다. 점검 모드를 켜고 사용자가 적은 시간에 손으로 한다(docs/deploy.md). 배포 워크플로는 옮겨 가지 않은 VM(`active_color` 가 없음)에는 아무것도 올리지 않고 멈춘다.

## 근거
- VM 한 대 · 무료 범위에서 끊김을 없애는 가장 작은 방법이다. 이미 있는 Caddy 의 다시 읽기만 쓰고 새 구성 요소가 없다.
- 받는 쪽을 바꾸기 전에 새 색의 `/health` 를 보므로, 뜨지 않는 jar 는 사용자에게 닿지 않는다(지금은 띄워 본 뒤에 되돌린다).
- 일꾼이 스스로 기다리는 때(빈을 없앨 때)에는 서비스 빈과 박동 일정이 이미 없어진 뒤다. 그래서 기다림을 그보다 앞(웹 서버가 요청을 그만 받은 직후)에 둔다.
- 256MB: 오늘 운영이 이 상한으로 214MiB 를 쓰고 있다. 320MB 처럼 올리면 겹칠 때 스왑에 더 가까워진다.

## 대안
- 두 색을 다 upstream 에 두고 Caddy 상태 검사로 고르기(파일 바꾸기 없음): 겹치는 동안 두 버전이 함께 받고, 옛 색이 닫히는 순간의 POST 가 실패할 수 있다.
- 지금처럼 다시 만들되 점검 모드로 가리기: 끊김을 안내할 뿐 없애지 않는다.
- VM 두 대 + 로드 밸런서 · 쿠버네티스: 무료 범위 밖이고 혼자 운영하기에 크다.
- Postgres 복제 · 장애 넘기기: VM 한 대라 하지 않는다. DB 재시작이 필요한 일은 점검 모드로 한다.

## 결과·재검토 조건
- 배포가 옛 색의 일이 끝날 때까지 기다리므로 길어질 수 있다(보통 몇 초, 생성 중이면 최대 약 5분).
- VM 에서 `docker compose up -d` 를 서비스 이름 없이 부르면 두 색이 다 뜬다(받는 쪽은 그대로라 끊기지는 않지만 메모리를 쓴다). 절차는 늘 서비스 이름을 적는다(docs/deploy.md).
- 다시 본다: 두 JVM 이 겹칠 때 스왑을 계속 쓰거나 응답이 느려질 때(상한을 낮추거나 더 큰 VM), 서버가 여러 대가 될 때(로드 밸런서로), 생성이 180초 안에 끝나지 않아 FAILED 가 자주 보일 때.

# 029. 심층 리포트를 나 탭 풀이 · 시기 풀이 둘로 나누고, 풀이 종류마다 "받을 수 있나" 확인 자리를 둔다

> 상태: 활성 · 결정일 2026-11-20(소유자 질문 · 답 4번 "따로따로 봐야지 시기 쪽이랑 나 탭에 있는 거", "돈을 받을 거야 이거. 1.1.0 부터는" → "그러자 따로 받자" · 구현 승인 "그 작업해야지 지금까지 만들어 놓은 것들은") · 원본: 앱 저장소 `docs/raw/2026-11-20-session-owner-qna-home-me-timing.md` 4번 · 앱 결정 050(풀이 둘을 따로 받는다) · 결정 008 의 "시기는 심층 리포트의 한 영역" 을 대체한다 · 계획 docs/plans/2026-11-20-home-me-timing.md

## 맥락
- 지금 심층 리포트는 한 번의 `POST /reports` 로 네 영역(성격 · 관계 · 일 · 감정)과 시기를 함께 만든다(`report/ReportService.kt`, 모델 호출 5회, `reports` 테이블 한 행 · `unique(owner_id, chart_hash)`).
- 확정 시안은 "자세한 풀이 받기" 버튼이 두 곳에 있다: 나 탭(칩 다섯 — 성격 · 연애 · 관계 · 일 · 감정)과 시기 탭(지금 나의 시기 + 올해 · 인생). 소유자는 둘을 따로 받게 했고, 1.1.0 부터 돈을 받는다고 했다(4번).
- 결제(RevenueCat)는 지금 만들지 않는다. 1.0.0 은 둘 다 무료다.

## 결정
1. **풀이는 두 종류다**: 나 탭 풀이(`ME`)와 시기 풀이(`TIMING`). 경로가 따로다 — `POST /me-report` · `GET /me-report`, `POST /timing-report` · `GET /timing-report`. 상태 규칙(`NONE` · `WRITING` · `FAILED` · `DONE`, 202 로 바로 답함, `active_at` 15초 · 2분 넘게 끊기면 `FAILED`, 출생 정보를 고치면 `NONE`)은 지금 리포트와 같다.
2. **저장**: 새 테이블 `detail_reports`(V22) 하나에 `kind`(`ME` · `TIMING`)로 나눈다. `unique(owner_id, kind, chart_hash)`. 꼴은 `reports`(V4 · V9)와 같다. 일꾼은 지금의 `reportExecutor` 를 같이 쓴다(동시에 나가는 모델 호출 상한이 하나로 남는다).
3. **생성 한도**(결정 022 · 023): 두 `POST` 는 각각 "모델 생성을 시작하는 요청" 이다. 자리를 잡은 뒤 한 번 센다(영역이 여럿이어도 요청 하나 = 한 번).
4. **"받을 수 있나" 확인 자리**: 생성을 시작하기 직전(한도를 세기 전) 서비스가 `EntitlementPolicy.allows(ownerId, kind)` 를 부른다. 1.0.0 은 언제나 `true` 다(클래스 하나 · 함수 하나, 인터페이스를 두지 않는다 — 골든 룰 "단일 구현 인터페이스 금지"). 1.1.0 에 이 함수 안에 결제 확인만 끼운다. 거절할 때의 응답 이름은 402 `PURCHASE_REQUIRED` 로 예약한다(1.0.0 에는 나오지 않는다 · 계약 표에 "예약" 으로 적는다). 이미 `DONE` 인 풀이를 다시 읽는 `GET` 과 `POST` 는 확인하지 않는다.
5. **가입 때 만드는 것**은 별명(요약 해석)뿐이고 이번 달은 계산이다(결정 032). 두 풀이는 사용자가 버튼을 눌러야 만든다.
6. **옛 경로**(`POST /reports` · `GET /reports/me`)는 앱이 새 경로로 바꾸고 새 테스트앱 빌드가 나올 때까지 그대로 둔다. 그 뒤 정리 PR(계획 S⑦)에서 뺀다 — 공용 API 제거라 제목에 적고 소유자가 확인한다. `reports` 테이블과 그 행은 읽지 않게 될 뿐 지우지 않는다(지우기는 범위 밖).
7. 완성되면 이벤트를 낸다: 나 탭 풀이 `MeReportDone(ownerId)`, 시기 풀이 `TimingReportDone(ownerId)`(지금 `report.ReportDone` 의 자리 — 알림함이 듣는다, 결정 035). 이벤트에 글 · 출생 정보는 싣지 않는다.

## 근거
- 소유자가 따로 받게 했고(4번), 1.1.0 에 나 탭 · 시기를 따로 또는 묶어 팔 수 있어야 한다. 한 행 · 한 상태로는 한쪽만 받은 상태를 나타낼 수 없다.
- 테이블 하나에 `kind` 로 두면 상태 · 심장박동 · 멈춤 판정 코드를 두 벌로 만들지 않는다. `reports` 의 유일 제약을 바꾸는 대신 새 테이블을 더해 마이그레이션은 더하기만 한다.
- 확인 자리를 지금 두면 1.1.0 에 서비스 흐름(한도 · 자리 잡기 · 실패 처리)을 다시 짜지 않고 함수 한 곳만 바꾼다.

## 대안
- 지금 리포트를 그대로 두고 앱이 화면만 둘로 나누기 — 따로 받을 수 없고, 한쪽만 결제한 사람을 나타낼 수 없다.
- `reports` 에 `kind` 칸을 더하기 — 유일 제약을 지우고 다시 거는 파괴적 변경이 들어가고, 옛 행의 `kind` 를 채워야 한다.
- 결제를 지금 함께 만들기 — 소유자가 1.1.0 부터라고 했고, 1.0.0 은 무료다.

## 결과·재검토 조건
- 1.1.0 결제 계획에서 `EntitlementPolicy` 의 판정(구독 · 단건 · 묶음, 출생 정보를 고친 뒤 다시 받기)을 새 결정으로 정한다. 그때 402 `PURCHASE_REQUIRED` 를 실제로 쓴다.
- 나 탭 풀이의 모양은 결정 030, 시기 풀이의 모양은 결정 033.
- docs/architecture.md 의 계약 표 · "리포트 상태" · "데이터" 는 계획 S② · S③ 의 PR 에서 같은 커밋으로 고친다.

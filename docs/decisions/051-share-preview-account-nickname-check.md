# 051. 공유 카드 미리 받기 · 로그인 중 닉네임 확인

> 상태: 활성 · 결정일 2026-11-21(소유자 결정, 조율 세션 47 이 전함) · 결정 012 · 036(공유 카드) · 025(닉네임)에 더한다 · 앱 계약 추가(바뀌는 것은 없다)

## 맥락
- 앱은 공유 화면에 들어올 때 카드를 먼저 보여 주고 싶다. 지금은 `POST /shares` 뿐이라, 보여 주기만 해도 공유 행 · 공개 식별자 · 감사 기록이 생긴다(공개 주소가 생긴 셈).
- 마이에서 닉네임을 바꾸기 전에 쓸 수 있는지 물을 곳이 없다. `POST /auth/nickname-check` 는 가입권으로만 묻는다.
- 문의 답변 푸시 본문은 지금 그대로 둔다(답 첫 줄을 넣지 않는다 — 소유자 결정).

## 결정
1. **`POST /shares/preview`**: `POST /shares` 와 같은 요청 · 같은 카드 · 같은 400 · 404(남의 것 · 없는 글). 응답은 `{ card }` 뿐이고 **공유 행 · `shareId` · 감사 기록을 만들지 않는다.** 속도 제한도 같다(`POST /shares` 처럼 없음). 카드 만드는 코드는 하나이고 만들기만 저장한다.
2. **`GET /account/nickname-check?nickname=`**(세션): `{ available: boolean }`. 규칙은 가입 중 확인 · `PATCH /account` 와 같다 — 앞뒤 공백을 떼고, 틀리면(없음 포함) 400 `INVALID_NICKNAME`, 영문 대소문자는 같은 이름, **내 지금 닉네임(대소문자만 다른 것 포함)이면 true.** 이용 정지 계정은 다른 세션 경로처럼 403.

## 근거
- 미리 보기만으로 공개 주소가 생기지 않아야 한다(결정 012 — 공유는 사용자가 공유를 누른 순간의 것만).
- 닉네임 확인은 바꾸기(`PATCH /account`)와 같은 판정(`nicknameTakenByOther`)을 써야 확인과 저장의 답이 어긋나지 않는다.

## 대안
- `POST /shares` 에 `dryRun` 칸 — 같은 경로에 저장 여부가 섞여 실수로 저장할 수 있다.
- 가입용 `POST /auth/nickname-check` 를 세션으로도 받기 — 가입권 · 세션 두 인증이 한 경로에 섞인다.

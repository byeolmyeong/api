# 031. 근거는 서버가 만든 후보(id)에서 모델이 고르고, 서버가 구조(`BasisItem`)로 바꿔 준다

> 상태: 활성 · 결정일 2026-11-20(소유자 질문 · 답 5번 "서버가 근거를 구조로 주고, 앱이 정해진 틀과 용어 사전으로 문장을 만든다" · 구현 승인) · 원본: 앱 저장소 `docs/raw/2026-11-20-session-owner-qna-home-me-timing.md` 5번 · 시안: 보드 12 · 12-1 · 12-8~12-12 · 14-3 · 14-4 · 11-4 의 "이렇게 풀이한 이유" · 앱 결정 054(이유 문장 · 용어 사전) · 계획 docs/plans/2026-11-20-home-me-timing.md

## 맥락
- 지금 근거는 낱말 목록이다: 문단마다 `basis[]` 에 `generation/Basis.kt` 의 `basisVocabulary(chart)`(천체 · 지점 이름, 상승점 · 중천, 놓인 별자리, 놓인 하우스)에서 고른 말을 담고, 구조 지정(enum)과 서버 대조(`BASIS_NOT_IN_CHART`)가 지킨다. 앱은 그 낱말을 문단 머리에 그대로 보인다.
- 시안은 근거를 문장으로 보인다: "태어날 때 나의 중심(해)이 자유로운 물병자리, 즐거움의 자리(5하우스)에 있었어요", "별 셋(행성 3개)이 즐거움의 자리(5하우스)에 모여 있었어요", "책임을 맡은 별(토성)이 나의 중심(해)과 부딪히는 각도(사분)에 있었어요", "마음(달)이 책임을 맡은 별(토성)이 다스리는 자리에 있었어요", 시기 "지금 책임을 맡은 별(토성)이 내 나의 중심(해)과 부딪히는 각도(사분)를 지나요", 그날 "그날 말을 맡은 별(수성)이 내 나의 중심(해)과 잘 어울리는 자리를 지나요". 낱말 목록으로는 "누가 어디에 · 무엇과 어떤 각도" 를 알 수 없다.
- "다스리는 자리"(달이 토성이 다스리는 염소자리에)는 지금 근거 말에 없는 종류다.
- 차트 글(`generation/ChartFacts.kt`)은 이미 천체 · 지점 · 상승점 · 중천 · 가장 많이 모인 곳 · 각도 쌍을 서버가 계산해 준다(세는 일을 모델에게 맡기지 않는다).

## 결정
1. **근거 하나의 구조 `BasisItem`**(`kind` 로 나눈다):
   - `{ kind: "PLACEMENT", body: Body | Angle, sign: Sign, house?: 1..12 }` — 천체(또는 `ASC` · `MC`)가 놓인 별자리 · 하우스
   - `{ kind: "CLUSTER", house: 1..12, bodies: Body[] }` — 한 하우스에 천체 3개 이상
   - `{ kind: "ASPECT", a: Body | Angle, b: Body | Angle, type: AspectType }` — 태어날 때 두 점의 각도
   - `{ kind: "RULER", body: Body, ruler: Body }` — 천체가 놓인 별자리를 다스리는 별(전통 지배성: 화성 양 · 전갈 / 금성 황소 · 천칭 / 수성 쌍둥이 · 처녀 / 달 게 / 해 사자 / 목성 사수 · 물고기 / 토성 염소 · 물병)
   - `{ kind: "TRANSIT", mover: Body, target?: Body | Angle | "VERTEX", type?: AspectType, house?: 1..12 }` — 지나가는 별이 내 점에 각도를 이루거나(target + type) 내 하우스를 지난다(house)
   - `Angle` = `"ASC"` | `"MC"`. 글자는 지금 `Chart` 의 `body` · `sign` · `type` 과 같다.
2. **`Reason` = `{ when: "BIRTH" | "NOW" | "DAY", items: BasisItem[1..2] }`** — 문단 · 실천 묶음 하나의 "이렇게 풀이한 이유". `BIRTH` 는 태어날 때(요약 해석 · 나 탭 풀이), `NOW` 는 지금 지나는 시기(시기 풀이의 구간), `DAY` 는 그날(이번 달 · 그날의 하늘). `TRANSIT` 은 `NOW` · `DAY` 에만, 나머지 종류는 `BIRTH` 에만 나온다. 문장은 앱이 정해진 틀과 용어 사전으로 만든다(앱 결정 054) — 서버는 문장을 보내지 않는다.
3. **후보 id 와 고르기**: 서버가 그 차트(시기 · 그날이면 그 통과 목록)에서 근거 후보를 모두 만들고 id 를 붙여 프롬프트의 "[근거 후보]" 로 준다. id 꼴: `P-SUN` · `P-ASC`(놓인 자리), `C-5`(하우스 모임), `A-SATURN-SUN-SQUARE`(각도, 정확한 각도에 가까운 것부터), `R-MOON`(다스리는 별), `T-SATURN-SUN-SQUARE` · `T-JUPITER-H7`(통과). 응답 구조의 근거 칸 `basis` 는 그 id 들의 enum 이고 1~2개를 고른다. 서버는 id 를 `BasisItem` 으로 바꿔 `reason.items` 에 넣는다. 구조상 지어낸 근거는 나올 수 없고, 개수가 틀리면 `MALFORMED` 로 버리고 다시 생성한다(지금 규칙 그대로 2회까지).
4. **후보의 범위**(내 결정, 기본값): `PLACEMENT` 는 천체 10개 + (시각을 알면) `ASC` · `MC`. `CLUSTER` 는 시각을 알 때 3개 이상 모인 하우스만. `ASPECT` 는 지금 `chart.aspects`(행성 10개 사이) + 시각을 알면 해 · 달과 `ASC` · `MC` 의 합 · 충 · 사분. `RULER` 는 해 · 달 · 상승점의 별자리를 다스리는 별(그 별 자신이 아닐 때). 지점(북쪽 교점 · 릴리스 · 행운점 · 버텍스)은 후보에 넣지 않는다(시안에 없는 용어 — 차트 글에는 지금처럼 남긴다).
5. **시각을 모르면** 하우스가 든 후보(`PLACEMENT.house` · `CLUSTER` · 하우스 통과)와 `ASC` · `MC` 가 든 후보를 만들지 않는다. 지금 "시각을 모르면 하우스 · 상승점 · 중천을 넣지 않는다" 규칙의 연장이다.
6. **이 풀이에 쓰인 별 `Star`** = `{ body?: Body | Angle, sign?: Sign, house?: 1..12, count?: Int }`. 서버가 그 영역 문단들의 `reason` 에서 겹치지 않게 앞에서부터 1~3개를 만든다(모델이 고르지 않는다): `PLACEMENT` → body + sign(시안 "나의 중심 · 물병자리"), `CLUSTER` → house + count("즐거움의 자리 · 별 셋"), `ASPECT` · `RULER` → 앞쪽 별 하나(body 만, "책임을 맡은 별 · 토성"), 감정 영역처럼 하우스를 보이고 싶은 `PLACEMENT` 는 house 만 줄 수도 있다(시안 "집과 가족의 자리 · 4하우스" — 영역 지시문이 하우스를 앞세운 문단일 때, 내 결정).
7. **쓰는 곳**: 요약 해석 문단(`sections[].reason`), 나 탭 풀이 문단 · 연애 실천 묶음(결정 030), 시기 풀이 구간(결정 033), 이번 달 눈여겨볼 날(결정 032, 모델 없이 서버가 바로 만듦), 그날의 하늘(결정 034).
8. **옛 칸**: 요약 해석의 `sections[].basis[]`(낱말)은 옮기는 동안 서버가 `reason` 에서 만들어 함께 보낸다(`basisVocabulary` 의 말). 정리 PR(계획 S⑦)에서 뺀다. `basisVocabulary` · `synastryBasisVocabulary` 는 궁합 글이 그대로 쓴다(궁합은 이 결정의 범위 밖).

## 근거
- 문장을 서버나 모델이 쓰면 화면 문구가 두 저장소에 흩어지고(골든 룰 "문구는 strings"), 모델이 "물병자리" 같은 용어를 본문에 섞을 길이 열린다. 구조를 주면 앱이 용어 사전 하나로 같은 틀을 쓴다.
- id 에서 고르게 하면 지금의 "근거 대조" 를 구조 지정이 대신한다 — 차트에 없는 근거가 응답에 들어올 수 없다.
- 계산(모임 · 각도 · 다스리는 별 · 통과)은 서버의 순수 함수가 한다(골든 룰 "차트 계산은 chart 패키지에서만").

## 대안
- 지금처럼 낱말 목록을 주고 앱이 문장을 짐작하기 — "토성이 해와 사분" 처럼 둘 사이 관계를 알 수 없다.
- 모델이 근거 문장을 쓰게 하기 — 용어 금지 규칙과 부딪히고, 틀린 관계를 지어낼 수 있다.
- 근거 구조를 모델이 직접 채우기(body · sign · house 를 칸으로) — 별자리 · 하우스를 틀리게 적어도 구조로는 막을 수 없다. id 고르기가 더 단순하고 안전하다.

## 결과·재검토 조건
- `generation/Basis.kt` 에 후보 만들기(`basisCandidates(chart)` · 통과용 `transitCandidates(...)`)와 id → `BasisItem` 바꾸기가 더해진다. 다스리는 별 표는 `chart` 패키지의 순수 함수로 둔다.
- 현대 지배성(물병 → 천왕성 등)을 쓰자는 의견이 나오면 새 결정으로 바꾼다. 지금은 전통 지배성 하나만 쓴다(시안 "달이 토성이 다스리는 자리" 가 염소자리).
- docs/architecture.md 의 "글 생성 규칙"(근거 대조 · 근거에 쓸 수 있는 말)과 계약 표는 계획 S① 의 PR 에서 같은 커밋으로 고친다.

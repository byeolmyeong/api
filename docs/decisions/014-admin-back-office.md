# 014. 관리자 API 를 둔다 (앱 사용자와 완전히 분리된 계정·세션, 문의 관리·수치·FAQ)

> 상태: 활성 · 결정일 2026-11-12(소유자) · 계약은 docs/architecture.md "관리자 API" · 결정 013 의 2번("관리 화면도 메일 발송도 만들지 않는다")에서 **관리 화면 부분만** 이 결정이 바꾼다(메일 발송은 여전히 없다). 번호 011·012 는 다른 작업 브랜치가 쓰고 있다.
> 2026-11-20: 사용자 관리 · 현황 v2 · 접속 차트 · 관리자 추가 방식(임시 비밀번호) · 광고 푸시 발송은 결정 043 이 더하고 바꿨다(이 결정의 나머지는 그대로).
> 2026-11-20: 문의 관리의 찾기 · 작성자 · 답 · 임시 저장 · 상태 `ANSWERED` 는 결정 039, 앱 설정의 최신 버전은 결정 040 이 더했다.

## 맥락
- 문의는 저장만 되고 소유자가 SQL 로 읽는다(결정 013). 처리 상태를 적을 곳도, 누가 처리했는지 남길 곳도 없다.
- 소유자가 2026-11-12 에 관리 화면을 두기로 했다. 화면은 새 저장소(`byeolmyeong-admin`, 웹)가 맡고 이 저장소는 API 만 만든다. 범위는 문의 관리 + 현황 수치 + FAQ 편집이고, 관리자는 여러 명(아이디 + 비밀번호)이며 누가 무엇을 처리했는지 남긴다.
- 앱 사용자의 로그인(`accounts`·`sessions`)은 소셜 로그인으로 갈 것이고 비밀번호가 없다. 관리자는 성격이 다르다.

## 결정
1. **관리자 계정과 세션은 앱 사용자와 테이블부터 따로 둔다**: `admin_accounts`·`admin_sessions`. `accounts`·`sessions` 와 아무 관계가 없다. `/admin/**` 는 관리자 세션만, 그 밖의 경로는 사용자 세션만 받는다. 서로의 토큰은 401 이다(두 방향 모두 테스트).
2. **경로 나누기**: 사용자 세션 검사(`auth.SessionInterceptor`)는 `/admin/**` 를 보지 않고, 관리자 세션 검사(`admin.AdminSessionInterceptor`)가 `/admin/**` 전부를 본다(로그인 `POST /admin/auth/login` 만 뺀다). 없는 경로도 `/admin/` 아래면 401 이다. `auth` 는 `admin` 을 모른다 — 경로 글자(`/admin/**`)만 안다.
3. **비밀번호는 bcrypt**(Spring Security Crypto 의 `BCryptPasswordEncoder`, 강도 12 — 설정 `byeolmyeong.admin.bcrypt-strength`). 의존성은 `spring-security-crypto` 하나만 더한다. Spring Security 의 웹 쪽(필터 체인)은 들이지 않는다 — 세션 검사는 이미 인터셉터로 하고 있고(CORS 헤더가 먼저 붙어야 한다), 필터 체인을 들이면 모든 경로의 기본 동작이 바뀐다.
   - 비밀번호는 10자 이상이고 UTF-8 로 72바이트 이하다(bcrypt 가 72바이트까지만 본다. 넘으면 잘라 받지 않고 거절한다).
   - 없는 아이디와 틀린 비밀번호와 비활성 계정은 같은 답(401 `INVALID_CREDENTIALS`)이고, 없는 아이디에도 가짜 해시로 같은 계산을 해서 걸리는 시간을 맞춘다. 비교는 라이브러리의 일정 시간 비교다.
   - 로그인 시도는 주소(IP)별·아이디별로 10분에 정해진 수까지(`byeolmyeong.rate-limit.admin-login-per-ip` 20, `admin-login-per-id` 5). 이미 있는 `web.RateLimiter` 를 쓴다. 성공한 로그인도 센다(단순하게).
4. **관리자 세션**: 토큰은 무작위 32바이트, DB 에는 SHA-256 해시만(사용자 세션과 같은 방식). **로그인한 때부터 12시간 뒤 끝난다**(`byeolmyeong.admin.session-hours`). 쓰는 동안 늘어나지 않는다(요청마다 DB 를 쓰지 않으려고). 로그아웃하면 그 행을 지운다. 끝난 행은 누가 로그인할 때마다 지운다.
5. **첫 관리자**: 서버가 뜰 때 관리자가 한 명도 없고 환경 변수 `ADMIN_BOOTSTRAP_ID`·`ADMIN_BOOTSTRAP_PASSWORD` 가 둘 다 있으면 그 값으로 첫 관리자를 만든다(표시 이름은 아이디와 같다). 하나라도 없거나 규칙에 안 맞으면 만들지 않고, 관리자가 없으니 `/admin/**` 는 전부 닫힌 채다. 관리자가 한 명이라도 있으면 두 변수는 읽지 않는다. 비밀번호는 로그에 남기지 않는다.
6. **관리자 관리**: 관리자는 누구나 다른 관리자를 만들고 끄고 켤 수 있다(역할 구분 없음). 자기 자신은 끌 수 없고, 마지막 남은 활성 관리자는 끌 수 없다. 끄면 그 관리자의 세션을 모두 지운다. 관리자를 지우는 기능은 없다(처리 기록이 그 관리자를 가리킨다). 비밀번호는 자기 것만 바꾼다(바꾸면 자기의 다른 세션은 끝난다).
7. **문의 관리**: `inquiries` 에 상태(`NEW`·`IN_PROGRESS`·`DONE`, 어느 쪽으로든 바꿀 수 있다)·관리자 메모·처리한 관리자·처리한 때를 더한다. 상태나 메모를 바꿀 때마다 바꾼 관리자와 그때를 적는다(마지막 한 번만 남는다 — 이력 테이블은 두지 않는다). 계정을 지우면 문의가 함께 지워지는 것은 그대로다.
   - 문의의 주인은 계정 id 를 그대로 내려보내지 않고 `ownerRef`(계정 id 의 SHA-256 앞 12자)로 준다 — 같은 사람이 보낸 문의를 묶어 볼 수 있을 뿐, 계정을 찾는 열쇠가 아니다. 출생 정보는 어떤 관리자 응답에도 없다.
8. **수치**: `GET /admin/stats` 는 개수만 준다. `admin` 패키지는 다른 기능 패키지(`reading`·`report`·…)를 부를 수 없으므로(ArchUnit) **테이블을 읽기만 하는 자기 SQL**(`AdminStatsRepository`)로 센다. 다른 기능의 서비스에 "개수 세기" 를 더하고 이벤트로 모으는 것보다 훨씬 작고, 읽기뿐이라 다른 기능의 규칙을 깨지 않는다. 치르는 값: 테이블·열 이름이 바뀌면 이 SQL 도 고쳐야 한다(수치 테스트가 모든 테이블에 행을 넣고 세므로 마이그레이션이 어긋나면 테스트가 깨진다).
   - 저장되지 않는 실패(요약 해석·방향성 제시·궁합 요약의 생성 실패, 줄이 차서 거절된 요청)는 DB 에 없어 셀 수 없다. 수치에 넣지 않는다. 리포트의 `FAILED` 는 행으로 남은 것만이다.
9. **FAQ**: 테이블 `faqs`. 쓰기(만들기·고치기·지우기·순서·공개)는 `admin` 이, 공개 읽기(`GET /faqs`, 세션 없음)는 새 패키지 `faq` 가 한다. 두 패키지는 코드로 서로를 모르고 같은 테이블만 본다(8번과 같은 방식). `GET /faqs` 는 로그인 전 경로 목록에 **GET 만** 더하고, 주소별 분당 제한(`byeolmyeong.rate-limit.faqs-per-minute` 120)과 `Cache-Control: public, max-age=300` 을 붙인다. 처음 글은 마이그레이션에 넣지 않는다(관리 화면으로 넣는다).
10. **CORS**: 관리 화면의 주소는 `byeolmyeong.cors.admin-allowed-origins`(환경 변수 `ADMIN_ALLOWED_ORIGINS`)에 따로 적는다. `/admin/**` 는 이 주소만, 나머지 경로는 앱의 주소(`ALLOWED_ORIGINS`)만 허용한다. 서로의 주소는 서로의 경로에서 거절된다. 비어 있으면 `/admin/**` 는 어떤 브라우저 출처도 허용하지 않는다.
11. 로그에는 이벤트 이름과 사유 코드만 남긴다. 아이디·비밀번호·토큰·문의 글·메모·FAQ 글은 남기지 않는다.

## 버린 대안
- `accounts` 에 역할 칸을 더해 관리자를 앱 사용자의 한 종류로 — 소셜 로그인 계정에 비밀번호가 생기고, 토큰 하나가 두 세계를 다 열 수 있게 된다. 계정 삭제("모두 지운다")가 관리자의 처리 기록과 얽힌다.
- Spring Security 전체 — 위 3번.
- argon2 — Spring Security Crypto 의 구현은 Bouncy Castle 이 더 필요하다. bcrypt 는 추가 의존성이 없다.
- 쓰는 동안 늘어나는 세션(마지막 사용부터 N시간) — 요청마다 쓰기가 생긴다. 관리 화면은 하루 한 번 다시 로그인해도 된다.
- 수치를 기능마다의 서비스에서 모으기 — 8번.
- 문의 처리 이력 테이블 — 요청은 "누가 처리했는지" 까지다. 필요해지면 더한다.
- 관리자 역할(최고 관리자·일반) — 요청에 없다.

## 영향
- 새 패키지 `admin`·`faq`(둘 다 기능 패키지: 다른 기능을 모른다. `admin` 은 `web` 만, `faq` 는 `web` 도 필요 없다). `V12__admin.sql`(V10 은 다른 브랜치). `web.CorsConfig`·`web.RateLimitConfig`·`auth` 의 로그인 전 경로 목록이 경로 글자를 더 안다.
- 결정 013 의 "소유자가 테이블을 직접 읽는다" 는 관리 화면이 생기면 필요 없어진다(SQL 은 여전히 된다). 메일 발송은 여전히 없다 — 답장은 관리자가 `replyEmail` 로 직접 보낸다.
- 로그인 제한은 서버 메모리의 고정 창이다(`web.RateLimiter` 의 한계 그대로). 아이디별 제한 때문에 남이 아이디를 알면 그 관리자의 로그인을 10분씩 막을 수 있다 — 관리자 아이디는 공개하지 않는다.
- [확인 필요] 소유자: ① 비밀번호를 잊은 관리자를 다른 관리자가 다시 설정해 주는 기능이 없다(지금은 새 계정을 만들어 준다. 관리자가 한 명뿐인데 잊으면 DB 에서 그 행을 지우고 환경 변수로 다시 만든다). ② 관리자가 문의 글과 답장 이메일을 본다는 것이 개인정보 처리방침에 들어가야 하는지. ③ 운영에서 프록시 뒤에 서버를 두면 주소(IP)별 제한이 프록시의 주소 하나로 묶인다(이미 있는 제한과 같은 문제 — `web/RateLimitConfig.kt` 의 주석).

# 025. 가입 때 닉네임(필수)과 마케팅 수신 동의(선택)를 받고, GET/PATCH /account 로 보고 바꾼다

> 상태: 활성 · 결정일 2026-11-19(소유자, 앱 결정 039) · 결정 021 의 "이름은 받지 않는다"를 대체한다(이메일은 결정 024) · 계획 docs/plans/2026-11-19-account-nickname-consent.md · 계약은 docs/architecture.md "API 계약"

## 맥락
- 결정 021 은 계정에 이메일·이름을 두지 않았고, 결정 024 가 이메일(필수)을 더했다.
- 소유자 결정(2026-11-19, 앱 결정 039): 닉네임은 가입 화면에서 받는다. 마케팅(소식) 메일은 별도 선택 동의다(정보통신망법 50조) — 동의 여부와 동의/철회 일시를 남기고 마이에서 철회할 수 있어야 한다. 메일 발송과 2년마다의 수신 동의 확인은 나중의 계획이다.
- 처리방침 개정 공개됨(2026-11-19): 닉네임(필수), 마케팅 동의 여부·동의/철회 일시(선택), 보유는 탈퇴까지(동의 기록은 철회 또는 탈퇴까지).

## 결정
1. **계정 칸**(V20, 더하기만, null 허용): `accounts.nickname` · `accounts.marketing_consented_at`(null = 동의 안 함).
2. **닉네임**: `POST /auth/signup` 에서 필수, `PATCH /account` 로 바꿀 수 있다. 앞뒤 공백을 뗀 뒤 유니코드 코드 포인트 1~20개, 줄바꿈·제어 문자(Cc·Zl·Zp)는 안 된다, 중복은 된다. 틀리면 400 `INVALID_NICKNAME` — 가입권은 쓰지 않는다(고쳐서 다시 보낸다). 앞뒤 공백을 뗀 값을 저장한다.
3. **마케팅 수신 동의**: `POST /auth/signup` 의 `marketingConsent`(선택, 기본 false), `PATCH /account` 로 바꾼다. 동의하면 그때의 일시, 철회하면 null. 같은 값이면 일시를 바꾸지 않는다. 바뀔 때만 감사 기록(동의/철회, 닉네임·이메일 없이).
4. **`GET /account`** → `{ nickname, email, provider, marketingConsent, marketingConsentAt }`(없는 값은 null). **`PATCH /account { nickname?, marketingConsent? }`** → 같은 모양. 보낸 칸만 바꾼다. 소유자는 세션에서만 얻는다.
5. 닉네임은 로그·감사 기록·오류 응답에 넣지 않는다. 탈퇴하면 계정 행과 함께 지워진다.
6. 옛 계정(이 결정 전 가입)은 닉네임이 null 이다. 로그인을 막지 않는다.

## 근거
- 닉네임은 화면에 보이는 이름이라 중복을 막지 않고, 코드 포인트로 세어 이모지 하나를 한 글자로 본다.
- 동의를 일시로 남기면 "언제 동의했나"를 답할 수 있고(2년마다 확인 안내의 기준), 철회는 null 로 분명하다.

## 대안
- 닉네임 중복 금지 — 표시 이름일 뿐이고, 막으면 가입이 늘어진다.
- 동의를 참/거짓 칸 + 일시 칸 둘로 — 일시 하나로 둘 다 답한다.
- 닉네임을 가입 뒤 마이에서 — 소유자가 가입 화면으로 정했다(앱 결정 039).

## 결과·재검토 조건
- 서버가 가입 때 닉네임을 필수로 받으면 옛 가입 화면은 400 이다 — 스테이징은 앱의 새 가입 화면과 같은 날 올린다.
- 메일 발송 계획(S8)에서 동의 확인 안내·결과 메일을 더할 때 이 칸들을 쓴다.

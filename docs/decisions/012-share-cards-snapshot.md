# 012. 공유 카드는 공유하는 순간의 공개 글만 따로 저장하고(스냅샷), 그 글은 이벤트로 물어 얻는다

> 상태: 활성 · 결정일 2026-11-12 · 계획 태스크 10 · 제품 규칙의 원본: 앱 저장소 `docs/release-1.0.0.md` "F6", 앱 결정 010 · 번호 011 은 같은 때 다른 작업 브랜치가 쓴다 · docs/architecture.md 의 `GET /shared/{shareId}` 계약과 "데이터" 의 공유 식별자 설명을 바꾼다.

## 맥락
- F6: 공유 카드는 네 가지(요약 해석·궁합 점수·랭킹 TOP 3·다음 변곡점)이고, 링크는 로그인 없이 열리며 글과 "나도 보러 가기" 만 보여 준다. 출생 정보·근거·리포트 본문은 나오지 않는다.
- 카드에 실을 글은 `reading`·`synastry`·`report` 가 갖고 있는데, 기능 패키지는 서로 의존할 수 없다(결정 004).
- 지금까지의 설계는 글마다 공유 식별자를 두는 것이었다(`readings.share_id`, V3 · `Synastry.shareId` 는 미룸). 그런데 랭킹 카드와 다음 변곡점 카드는 한 행에 대응하지 않고(랭킹은 여러 궁합, 변곡점은 리포트의 한 줄), 궁합 점수 카드에는 서버가 모르는 값(공유하는 사람의 부를 이름)이 들어간다.
- 계정에는 부를 이름이 없다(공급자의 사용자 식별자만 받는다).

## 결정
1. **스냅샷.** 공유할 때 카드의 공개 필드만 JSON 으로 만들어 `shares` 표(V10)에 저장하고, `GET /shared/{shareId}` 는 그 JSON 을 그대로 준다. 조회할 때 다른 표를 읽지 않는다.
   - 조회 길에 근거·본문·소유자가 섞일 수 없다(그 값이 그 표에 없다). 공유한 뒤 글이나 랭킹이 바뀌어도 이미 올린 카드는 바뀌지 않는다(스토리에 올린 이미지와 링크가 같은 내용이다).
   - 계정을 지우면 `shares.owner_id` 의 `on delete cascade` 로 그 사람의 공유가 모두 사라지고 링크는 404 가 된다.
   - 출생 정보를 고치거나 궁합이 늘어도 예전 공유는 남는다. 없애려면 지운다(아래 5).
2. **만드는 길은 하나**: `POST /shares`(세션) `{ kind, … }` → `{ shareId, card }`. `card` 는 공개 조회가 주는 것과 같은 JSON 이다.
   - 같은 소유자가 같은 내용의 카드를 다시 만들면 새 행을 만들지 않고 있던 `shareId` 를 준다(`unique (owner_id, card_hash)`). 내용이 달라졌으면(랭킹이 바뀜, 이름 표시를 켬) 새 공유가 생긴다.
   - 공유할 글이 없으면(지금 차트의 요약 해석·완성된 리포트·그 관계 유형의 궁합이 없다, 남의 궁합이다, 다음 변곡점이 없다) 모두 404 `NOT_FOUND` 다.
3. **카드의 글은 그 글을 가진 기능에게 이벤트로 묻는다.** `share` 가 `ReadingCardRequested`·`ScoreCardRequested`·`RankingCardRequested`·`NextTurnCardRequested`(Spring 이벤트, 같은 스레드에서 바로 처리)를 내고, `reading`·`synastry`·`report` 의 서비스가 **이벤트에 적힌 소유자의 것일 때만** 답을 채운다. 아무도 답하지 않으면 404 다.
   - 이벤트에는 소유자·궁합 id·관계 유형과 답(글·점수·날짜)만 있고, JDK·Kotlin 표준·`chart` 의 타입만 쓴다. 근거·본문은 싣지 않는다.
   - 소유자 검사·"지금 차트" 판정·60점 미만 표시·랭킹 순서는 원래 그 일을 하던 서비스가 그대로 한다(`share` 가 다시 구현하지 않는다).
   - `ArchitectureTest` 의 이벤트 목록(`EVENTS`)과 docs/architecture.md 의 의존 규칙 표에 이 네 이름을 더한다. 규칙("기능 사이 연결은 Spring 이벤트로만")은 그대로다.
4. **공유 식별자**: 무작위 16바이트(128비트, `SecureRandom`)를 URL 용 Base64 로 적은 22자. `shares` 의 기본 키다.
   - `readings.share_id` 와 `Reading.shareId` 는 **더 쓰지 않는다**. 이 값으로 `GET /shared/…` 를 부르면 404 다. 응답의 필드와 열은 이번에 지우지 않는다 — 앱이 지금 `Reading.shareId` 가 글자인지 검사하고(앱 `src/lib/api.ts`), 열 삭제는 되돌릴 수 없는 변경이라 사람이 확인한다 [확인 필요: 앱이 읽지 않게 된 뒤 필드와 열을 지운다]. `Synastry.shareId` 는 만들지 않는다.
5. **지우기**: `DELETE /shares/{shareId}`(세션). 내 것이면 204 이고 그 뒤 링크는 404 다. 남의 것·없는 것은 404. 같은 카드를 다시 만들면 새 `shareId` 가 나온다(지운 링크는 살아나지 않는다).
6. **카드마다 싣는 것**(이것 말고는 없다)
   - 요약 해석 `READING`: `headline`(한 줄 총평) + `keywords[3]`. 요약 해석에는 키워드 필드가 없어서 **앞의 세 문단 제목**(15자 안팎, 용어 없음)을 쓴다. 강점은 한 문장씩이라 카드의 낱말 자리에 길고, 보완점과 마지막 문단(과제)은 남에게 보이기에 맞지 않는다 [확인 필요: 키워드를 따로 생성할지].
   - 궁합 점수 `SCORE`: `names[2]`(공유하는 사람, 상대) + `score` + `scoreLabel?` + `headline`. 공유하는 사람의 부를 이름은 서버에 없으므로 요청의 `myName`(앞뒤 공백을 뗀 1~20자)으로 받는다 [확인 필요: 앱이 이 이름을 어디서 얻는지 — 지금은 공유할 때 입력받아야 한다]. 관계 유형·키워드는 싣지 않는다.
   - 랭킹 `RANKING`: `relation` + `entries[1~3]{ name, score }`. 점수순 앞의 3명까지만 저장한다(4등부터는 표에도 없다). 이름은 기본이 이니셜이고 요청에 `showNames: true` 가 오면 적은 그대로다.
   - 다음 변곡점 `NEXT_TURN`: `year` + `season` + `theme`. 아래 8.
7. **이니셜**(서버가 만든다. 앱이 원래 이름을 받지 않게): 한글 음절은 첫소리 글자로(지영 → ㅈㅇ, 쌍자음은 그대로 ㅆ·ㄲ), 이미 낱자인 한글은 그대로, 그 밖의 글자·숫자는 이어진 덩어리의 첫 글자만 대문자로(Mike → M, 김 Min → ㄱM), 공백·기호·그림 문자는 뺀다. 남는 것이 없으면 `○`.
8. **다음 변곡점의 시기는 "해 + 계절"** 이다(F6 의 예 "2027년 봄").
   - "다음 변곡점" 은 리포트 시기의 `current.nextMilestone`(오늘 뒤의 첫 마디)이다. 앱의 시기 탭이 "다음 변곡점" 이라 부르는 것과 같다. 구간은 쓰지 않는다. 두 번째 토성 귀환이 지난 사람은 다음 마디가 없어 404 다.
   - 계절은 마디가 처음 정확히 겹치는 날(`date`)의 달로 정한다: 3~5월 `SPRING`, 6~8월 `SUMMER`, 9~11월 `AUTUMN`, 12·1·2월 `WINTER`. `year` 는 그 날의 달력 해다(2028년 1월도 12월도 "2028년 겨울").
   - `theme` 은 그 마디의 `title`(이 시기의 주제 한 줄)이다. `body`·날짜·만 나이·마디 종류는 싣지 않는다.
   - 생일을 되짚을 수 있는가(어림): 마디 종류는 카드에 없지만 나이로 짐작할 수 있다고 본다. 토성은 석 달에 보통 3~4°, 멈췄다 도는 무렵에는 1~2° 를 움직이므로, 카드의 계절에서 태어날 때의 토성 자리가 그만큼의 폭으로 좁혀진다. 토성이 그 폭을 지나는 데는 가장 빠를 때 2주쯤, 보통은 한두 달 이상이고 역행으로 같은 자리를 세 번 지날 수 있다. 그래서 알 수 있는 것은 "어느 해의 몇 주~몇 달 사이에 태어났다" 까지이고 날짜는 아니다. 태어난 해는 나이로 이미 짐작되는 값이다 [확인 필요: 이 폭도 좁다고 보면 `season` 을 빼고 해만 준다 — 상수 하나].
9. **요청 속도 제한**: `GET /shared/*` 에 주소별 분당 한도(`byeolmyeong.rate-limit.shared-per-minute`, 120)를 건다. 식별자를 마구 넣어 보는 것을 늦춘다. `POST /shares` 는 모델을 부르지 않아 따로 걸지 않는다.

## 대안
- 조회할 때마다 원본을 읽기(살아 있는 공유) — 저장이 줄지만 공개 길이 글·궁합·리포트 표를 모두 읽게 되고, 공유한 뒤 바뀐 내용(새로 1등이 된 사람의 이름 등)이 주인도 모르게 공개된다.
- `share` 가 다른 기능의 표를 SQL 로 직접 읽기 — 코드 의존은 없어 테스트는 통과하지만, 소유자 검사·60점 미만 표시·"지금 차트" 판정을 `share` 가 한 번 더 구현하게 되고 표 모양이 바뀌면 조용히 깨진다.
- 기능마다 공유 엔드포인트(`POST /readings/share` 등)를 두고 공통 저장소에 쓰기 — 공통 패키지를 하나 더 만들어야 하고(의존 규칙을 늘린다), 공개 필드를 정하는 곳이 네 군데로 흩어진다.
- 글마다 공유 식별자 열(기존 설계) — 랭킹·다음 변곡점·공유하는 사람의 이름을 담을 곳이 없다.
- 앱이 카드 내용을 보내고 서버는 저장만 — 누구나 이 서비스의 주소에 아무 글이나 올릴 수 있게 된다.

## 결과·재검토 조건
- 앱: 공유 버튼이 `POST /shares` 를 부르고 응답의 `card` 로 이미지를, `shareId` 로 주소(`/s/<shareId>`)를 만든다. 공유 페이지는 `GET /shared/{shareId}` 하나만 부른다.
- 초대로 연결된 궁합(태스크 9 의 나머지)이 들어오면 "두 사람 중 누구나 공유" 는 `synastry` 의 이벤트 답에서 풀린다(소유자 검사가 거기 있다). 그때 상대 계정이 지워지면 그 사람의 이름이 든 공유를 어떻게 할지 정해야 한다 [확인 필요].
- 공유가 오래 남는 것이 문제가 되면(만료) `shares.created_at` 으로 지운다. 지금은 만료가 없다.
- 서버가 여러 대가 되면 속도 제한을 다시 본다(지금은 서버 메모리).

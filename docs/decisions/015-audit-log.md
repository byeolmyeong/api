# 015. 감사 기록을 남긴다 (관리자와 사용자의 주요 행동 — "누가 무엇을 언제" 만, 서버에만)

> 상태: 활성 · 결정일 2026-11-12(소유자: "관리자 + 사용자 주요 행동") · 계약은 docs/architecture.md "관리자 API" 의 "감사 기록" · 결정 014 의 7번("이력 테이블은 두지 않는다")은 그대로다 — 이 기록은 문의의 처리 이력이 아니라 행동의 목록이다.

## 맥락
- 관리자가 여러 명이 됐다(결정 014). 누가 로그인했고 무엇을 바꿨는지는 지금 마지막 한 번(`handledBy`·`updatedBy`)만 남는다.
- 사용자 쪽은 어떤 행동이 있었는지 서버 로그에만 있고(이벤트 이름뿐, 누구인지 없음) 로그는 오래 두지 않는다.
- 소유자가 2026-11-12 에 관리자와 사용자의 주요 행동을 서버에 기록하기로 했다. 출생 정보나 글은 남기지 않고 "누가 무엇을 언제" 만 남긴다.

## 결정
1. **테이블 `audit_logs`(V13)** 한 곳에 넣는다: 일어난 때 · 행위자 종류(`ADMIN`·`USER`·`SYSTEM`) · 행위자 id(관리자 계정 id 또는 사용자 계정 id 의 글자, `SYSTEM` 은 null) · 행위자 표시(관리자는 그때의 로그인 아이디, 사용자는 `ownerRef`) · 행동 코드 · 대상 종류와 대상 id(없을 수 있다) · 결과(`SUCCESS`·`FAILURE`) · 덧붙임(`detail`, 작은 JSON).
2. **넣기만 한다.** 고치거나 지우는 API·코드가 없다. 보관 기한도 아직 없다(아래 "남은 일").
3. **개인적인 것은 한 글자도 넣지 않는다.** 출생 날짜·시각·장소, 이름, 이메일, 메모·문의·FAQ 의 글, 비밀번호, 토큰, 주소(IP)는 어느 칸에도 없다. `detail` 에는 코드 값만 넣는다(예 `{ "status": "DONE" }`·`{ "topic": "FUTURE" }`·`{ "platform": "ios", "minVersion": "1.2.0" }`).
   - 글자 값은 영문·숫자·`.`·`_`·`-` 40자 이하일 때만 저장한다(기록하는 쪽이 한 번 더 거른다 — 한글 글·이메일·긴 글은 이 모양이 아니다). 맞지 않는 값이 오면 `detail` 을 통째로 버리고 행은 남긴다.
   - 실패한 관리자 로그인은 "실패한 관리자 로그인이 있었다" 만 남긴다: 행위자는 `SYSTEM`(null), 시도한 아이디는 남기지 않는다(아이디 자리에 비밀번호를 잘못 넣는 일이 흔하다).
   - 공유의 대상 id(공유 식별자)는 남기지 않는다. 그 값은 로그인 없이 카드를 여는 열쇠다.
4. **계정을 지워도 기록은 남는다.** `audit_logs` 는 `accounts`·`admin_accounts` 를 가리키는 외래 키가 없다. 감사 기록은 "그 계정이 지워졌다" 까지 말할 수 있어야 하고, 그래서 3번이 필요하다.
   - 치르는 값: 계정 삭제는 "모두 지운다" 고 약속하는데, 지운 뒤에도 그 계정의 id(무작위 UUID)와 `ownerRef`, 어떤 행동을 언제 했는지는 남는다. 남는 값으로는 사람을 찾을 수 없지만(계정 행이 없다) 행동의 시각 목록은 남는다. **[확인 필요] 소유자: 개인정보 처리방침에 "서비스 이용 기록(행동 종류와 시각)은 계정 삭제 뒤에도 N 동안 보관한다" 를 적어야 하는지, 보관 기한을 얼마로 할지.**
5. **사용자를 가리키는 말은 `ownerRef`** 다(계정 id 의 SHA-256 앞 12자, 결정 014 의 문의와 같은 값). 관리자 응답에 계정 id 를 그대로 내보내지 않는다. 같은 값이라 감사 기록과 문의를 묶어 볼 수 있다. 계산은 `web.ownerRef` 한 곳으로 옮긴다(`admin` 과 `audit` 이 같이 쓴다).
6. **기능이 알리는 방법은 Spring 이벤트**다. 이벤트 타입 `AuditEvent`(행동 코드 `AuditAction`·행위자 `AuditActor` 포함)는 공통 패키지 `web` 에 둔다 — 기능 패키지들과 공통 패키지 `auth`(로그인·계정 삭제)가 모두 내야 하는데, `auth` 는 기능 패키지를 알 수 없고(ArchUnit) `web` 은 둘 다 쓸 수 있는 유일한 곳이다. 새 기능 패키지 `audit` 이 그 이벤트를 듣고 테이블에 넣는다. 다른 기능은 `audit` 을 모른다.
7. **기록이 본래의 일을 깨뜨리지 않는다.**
   - 듣는 쪽은 `@TransactionalEventListener(AFTER_COMMIT, fallbackExecution = true)`: 트랜잭션 안에서 낸 이벤트는 커밋된 뒤에만 기록되고(되돌려진 일에 `SUCCESS` 행이 남지 않는다), 트랜잭션 없이 낸 이벤트는 바로 기록된다.
   - 넣기는 자기 트랜잭션(`REQUIRES_NEW`)이고, 실패하면 삼키고 로그에 `event=audit_record_failed action=… error=…` 만 남긴다. 사용자의 요청은 그대로 성공한다. 치르는 값: 그 행동은 기록에서 빠진다(다시 넣지 않는다).
   - 이벤트는 그 일이 끝난 **뒤에** 낸다. 실패를 기록하는 곳(관리자 로그인 실패, 생성 실패)만 실패가 정해진 자리에서 낸다.
8. **무엇을 기록하나**(전체 목록과 `detail` 은 docs/architecture.md "감사 기록"):
   - 관리자: 로그인(성공·실패)·로그아웃·비밀번호 변경·관리자 만들기·끄기·켜기·첫 관리자(`SYSTEM`)·문의 한 건 보기·문의 처리·FAQ 만들기·고치기·공개·내리기·지우기·순서·앱 설정 변경(결정 016).
   - 사용자: 로그인·출생 정보 저장·요약 해석 생성·리포트 요청·궁합 만들기·궁합 리포트 요청·방향성 제시 생성·공유 만들기·지우기·문의 보내기·계정 삭제.
   - 글 생성은 **새 글을 실제로 만들었거나 만들기 시작했을 때만** 기록한다. 저장된 글을 다시 받는 요청은 기록하지 않는다. 요약 해석·방향성 제시·궁합 요약은 생성 실패(502)도 `FAILURE` 로 남긴다 — 결정 014 에서 "셀 수 없다" 던 실패가 여기에 처음 남는다. 리포트·궁합 리포트는 요청만 남긴다(뒤에서 끝난 결과는 그 행의 상태에 있다).
   - 목록 조회·감사 기록 조회·수치 조회는 기록하지 않는다(잡음). 문의는 한 건 보기만 기록한다 — 문의 글과 답장 이메일을 본 것이기 때문이다.
9. **조회는 관리자만**: `GET /admin/audit-logs`(새것부터, 쪽 나눔, 행위자 종류·행동·날짜·행위자로 거른다). 날짜는 한국 시간의 `YYYY-MM-DD` 이고 두 끝을 포함한다. `audit` 패키지가 갖지만 경로가 `/admin/` 아래라 관리자 세션 검사와 관리 화면의 CORS 가 그대로 걸린다(`audit` 은 `admin` 의 코드를 쓰지 않는다 — 경로 글자만 같다).

## 버린 대안
- 서버 로그만 — 누가 했는지가 없고, 오래 두지 않으며, 관리 화면에서 볼 수 없다.
- 계정을 지우면 그 사람의 기록도 지운다(`on delete cascade`) — "계정 삭제" 자체와 그 앞의 행동이 사라져 감사 기록의 쓸모가 없다.
- 지울 때 행위자를 null 로 바꾼다 — 같은 사람의 행동을 묶을 수 없고, 넣기만 한다는 규칙이 깨진다.
- 기능이 `audit` 의 서비스를 직접 부른다 — 기능 패키지는 서로 의존할 수 없다(결정 004). `auth` 도 부를 수 없다.
- `AuditEvent` 를 `audit` 에 두고 ArchUnit 의 이벤트 목록에 더한다 — 기능 패키지는 되지만 공통 패키지 `auth` 는 기능의 이벤트도 쓸 수 없다.
- 같은 트랜잭션에서 넣는다 — 감사 테이블의 실패가 사용자의 일을 되돌린다.
- 인터셉터에서 모든 요청을 기록한다 — "새 글을 만들었는지"·"만들었는지 고쳤는지" 를 경로만으로 알 수 없고, 저장본을 읽는 요청까지 쌓인다.

## 영향·남은 일
- 새 기능 패키지 `audit`(ArchUnit 의 기능 목록에 더한다), `web.AuditEvent`·`web.ownerRef`, `V13__audit_logs.sql`. `auth` 가 `web` 을 쓰게 된다(`web` 은 여전히 `auth` 를 모른다 — 순환 없음).
- 실패한 관리자 로그인마다 행이 하나 생긴다. 로그인하지 않은 사람이 행을 만들 수 있는 유일한 길이고, 로그인 제한(주소별 10분에 20번)이 그 속도의 상한이다. 제한에 걸린 요청(429)은 기록하지 않는다.
- **보관 기한이 없다.** 행은 계속 쌓인다. 기한과 지우는 작업은 4번의 [확인 필요] 가 정해지면 만든다.
- 서버가 기록 직전에 꺼지면 그 행동은 기록에서 빠진다(일은 됐고 행은 없다). 감사 기록을 "빠짐 없는 증거" 로 쓰려면 같은 트랜잭션에 넣어야 하는데, 7번과 맞바꾼 것이다.
- [확인 필요] 소유자: ① 4번(개인정보 처리방침·보관 기한). ② 관리자가 사용자의 행동 목록을 `ownerRef` 로 묶어 볼 수 있다는 것이 처리방침에 들어가야 하는지.

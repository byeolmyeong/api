# 030. 나 탭 풀이는 영역 다섯(연애를 더함)마다 정해진 칸을 주고, 요약 해석은 보완점 2개와 만든 때를 준다

> 상태: 활성 · 결정일 2026-11-20(소유자 질문 · 답 3번 "자세한 풀이에 연애 영역을 새로 넣어 같이 만든다" · 구현 승인) · 원본: 앱 저장소 `docs/raw/2026-11-20-session-owner-qna-home-me-timing.md` 3 · 4 · 5번 · 시안: 피그마 `UlZGMcMO4LidtzLlJl4KFv` 보드 12 · 12-8~12-12 · 앱 결정 048(나 탭) · 047(홈의 "별명을 받은 지 N일") · 결정 029(풀이 나누기) · 031(근거 구조) · 037("~기") · 038(일 방식) · 계획 docs/plans/2026-11-20-home-me-timing.md

## 맥락
- 지금 리포트의 영역은 성격 · 관계 · 일 · 감정 넷이고, 영역마다 제목 하나와 문단 4~6개다(`report/Report.kt` 의 `PARAGRAPHS_PER_AREA = 4..6`). 연애는 방향성 제시 `POST /directions {topic: LOVE}`(결정 009)가 따로 맡았다.
- 시안 나 탭 칩 다섯(12-8~12-12)은 공통으로 "○○ 님의 {영역}" · 제목 한 줄 · 키워드 3 · "이 풀이에 쓰인 별" 을 두고, 영역마다 모양이 다르다: 성격 한눈에 보기(빛나는 순간 2 · 지치는 순간 2) + 문단 01~04, 연애 작은 실천 3 + 이유 하나(문단 없음), 관계 가까워지는 모습 3단계 + 01~04, 일 일 방식 막대 셋 + 01~04, 감정 흔들릴 때 · 다시 편해지는 곳 + 01~04. 문단 본문은 두 문장이다.
- 시안의 요약 해석(보드 12)은 보완점이 2개인데 서버는 3개를 만든다(`reading/ReadingDraft.kt` 의 `CAUTION_COUNT = 3`). 홈의 "별명을 받은 지 N일" 에는 요약 해석을 만든 때가 필요하다 — `readings.created_at` 칸은 있으나(V3) 응답에 없다.
- 소유자: 이성 방향성 화면은 없애고 연애는 자세한 풀이의 영역으로 만든다(3번).

## 결정
1. **나 탭 풀이의 영역은 다섯이고 이 순서다**: `PERSONALITY` · `LOVE` · `RELATIONSHIP` · `WORK` · `EMOTION`. 영역마다 모델을 따로 부른다(다섯 호출을 한꺼번에 — 지금 리포트의 네 호출과 같은 방식). 틀린 영역만 다시 생성한다(영역마다 2회까지). 한 영역이라도 끝내 못 만들면 풀이 전체가 `FAILED` 이고 저장하지 않는다.
2. **영역마다 주는 칸**(`MeArea`): `area` · `title`(한 줄) · `keywords`(정확히 3, 겹치지 않음) · `stars`(1~3, 서버가 만든다 — 결정 031) · `paragraphs`(정확히 4개, 문단마다 `title` · `body`(두 문장 안팎) · `reason` — 결정 031). 영역별 칸:
   - `PERSONALITY` `glance` = `{ shining[2], tiring[2] }`(빛나는 순간 · 지치는 순간, 짧은 구절)
   - `LOVE` `practices` = `[{ title, body }]` × 3(제목은 "~기" 로 끝나는 실천, 결정 037) + 영역의 `reason` 하나. `paragraphs` 는 빈 배열이다.
   - `RELATIONSHIP` `closer` = `{ first, close, longtime }`(처음 만날 때 · 친해지면 · 오래된 사이, 짧은 한 줄)
   - `WORK` `workStyle` = `{ together, flexible, fast }` — 모델이 쓰지 않고 서버가 차트로 계산한다(결정 038)
   - `EMOTION` `shaken` = `{ when, comfort }`(흔들릴 때 · 다시 편해지는 곳)
3. **연애 영역의 성격**: 연인 사이에서 해 볼 만한 작은 실천이다(지금 `direction-love.md` 의 몫을 옮긴다). 관계 영역은 지금처럼 "나는 사람을 어떻게 대하는 사람인가"(친구 · 가족 · 연인 전반)이고 연애 조언이 아니다.
4. **요약 해석 v2**(`POST /readings`): 보완점(`cautions`)은 정확히 2개(시안), 강점은 그대로 3개. 응답에 `createdAt`(그 요약 해석을 만든 때, UTC ISO-8601)을 더한다. 문단은 지금처럼 시각을 알면 5 · 모르면 4이고, 문단마다 `reason`(결정 031)을 더한다. 새 모양은 저장 kind `SUMMARY_V2` 로 둔다(`readings` 의 `unique(owner_id, kind, chart_hash)` 그대로 — 마이그레이션 없음). 옛 `SUMMARY` 행은 읽지 않으므로 다음 `POST /readings` 가 새로 만든다(출시 전, 소유자 5번 "이미 만든 풀이 · 리포트는 새 모양으로 다시 만든다").
5. **옮기는 동안의 옛 칸**: 요약 해석의 `sections[].basis[]`(근거 낱말)와 `shareId` 는 새 앱이 테스트앱에 나갈 때까지 함께 보내고 정리 PR(계획 S⑦)에서 뺀다.
6. 검증(저장하기 전): 영역 · 키워드 · 문단 수, 빈 글, 근거가 없는 문단(구조상 enum 이라 지어낸 근거는 없다 — 결정 031), 연애 실천 제목의 "~기"(결정 037), 지금의 금지 표현(단정 · 운명 · 앞일의 끝맺음). 한 영역의 글에 숫자 · 퍼센트가 있으면 버린다(일 방식의 수치는 서버 값만 말한다).

## 근거
- 시안이 영역마다 칸을 다르게 그린다. 서버가 칸을 나눠 주면 앱은 글에서 숫자 · 단계를 뽑지 않고 그대로 그린다.
- 연애를 영역으로 넣으면 이성 방향성 화면과 관계 영역이 겹치지 않는다(소유자 3번). 다섯 영역을 한 번에 받으면 1.1.0 에 "나 탭 풀이" 한 상품으로 팔 수 있다(결정 029).
- 보완점 개수는 화면 쪽 결정이다. 확정 시안(보드 12)을 따른다.

## 대안
- 연애를 지금의 방향성 제시(`topic: LOVE`)로 남기고 칩에서 부르기 — 소유자가 이성 화면을 없앴고, 다른 경로 · 다른 저장이 되어 "나 탭 풀이를 받았나" 를 하나로 판정할 수 없다.
- 영역별 칸 없이 문단만 받고 앱이 꾸미기 — 막대 · 단계 · 한눈에 보기를 앱이 글에서 지어내야 한다.
- 요약 해석을 새 칸으로만 고치고 kind 를 그대로 두기 — 옛 행이 새 칸 없이 나가 앱이 깨진다.

## 결과·재검토 조건
- 새 프롬프트: `me-report.md`(공통) + `me-report-<영역>.md` 다섯 + 시각을 모르면 `report-time-unknown.md`. 옛 `report.md` · `report-<영역>.md` 넷은 S⑦ 에서 옛 경로와 함께 지운다.
- `direction-love.md` 와 `POST /directions {topic: LOVE}` 는 앱이 더 부르지 않는다(S⑦ 에서 뺀다).
- 시안이 보완점 개수를 바꾸면 이 결정의 4를 새 결정으로 바꾼다.
- docs/architecture.md 의 "글 생성 규칙"(요약 해석 · 리포트의 모양)과 계약 표는 계획 S① · S② 의 PR 에서 같은 커밋으로 고친다.

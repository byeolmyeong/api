# 026. 가입 때 약관 · 처리방침에 동의한 버전과 시각을 남기고, 푸시 수신 동의와 프로필 그림을 계정에 둔다

> 상태: 활성 · 결정일 2026-11-19(소유자 "바로 시작해") · 결정 021(가입권) · 024(이메일) · 025(닉네임 · 마케팅 동의) 위에 더한다(어느 것도 대체하지 않는다) · 계획 docs/plans/2026-11-19-signup-terms-push-consent.md · 계약은 docs/architecture.md "API 계약"

## 맥락
- 앱 온보딩(앱 계획 `2026-11-19-onboarding-design.md`, 피그마 보드 "6 약관 동의")에서 약관 단계가 닉네임보다 먼저 온다: 필수 2(이용약관 · 개인정보 수집 · 이용) · 선택 2(푸시 알림 받기 · 마케팅 정보 수신). 마케팅 정보 수신은 결정 025 가 이미 맡는다.
- 지금 서버는 사용자가 어느 판의 약관에 언제 동의했는지 남기지 않는다. 소유자는 약관 동의를 증명할 수 있어야 한다.
- 소유자(2026-11-19): 야간(21~08시)에는 광고를 보내지 않으므로 야간 광고 수신 동의는 받지 않는다. 프로필은 브랜드 그림 8종(앱 `assets/brand/avatar-1~8.svg`) 중 하나를 가입 때 고른다.
- 랜딩의 약관(byeolmyeong.com/terms) · 처리방침(byeolmyeong.com/privacy) 시행일은 2026-11-19 다.

## 결정
1. **계정 칸**(V21, 더하기만, 모두 null 허용 — 옛 계정 때문에. 있던 행은 채우지 않는다): `terms_version` · `terms_agreed_at` · `privacy_version` · `privacy_agreed_at` · `push_consented_at`(null = 동의 안 함) · `avatar smallint`(1~8 check, null = 옛 계정).
2. **약관 버전은 서버 설정 한 곳**: `byeolmyeong.legal.terms-version` · `byeolmyeong.legal.privacy-version`(지금 둘 다 `2026-11-19`). 비어 있으면 서버가 시작하지 않는다 — 비면 모든 가입이 막히므로 배포의 상태 확인에서 바로 드러나게 한다.
3. **가입**(`POST /auth/signup`)은 `termsVersion` · `privacyVersion` 이 서버의 지금 버전과 **둘 다 글자 그대로 같을 때만** 받는다. 없거나 다르면 400 `TERMS_REQUIRED` 이고 가입권은 쓰지 않는다(앱이 약관 단계로 돌아가 같은 가입권으로 다시 보낸다). 동의 시각은 서버 시각이다 — 앱이 보낸 시각은 받지 않는다. 새 계정에만 저장한다: 남은 가입권으로 다시 와서 계정이 이미 있으면 약관 칸을 덮어쓰지 않는다.
4. **판정 순서**: 가입권(401 `SIGNUP_EXPIRED`) → 약관(400 `TERMS_REQUIRED`) → 닉네임(400 `INVALID_NICKNAME`) → 프로필(400 `INVALID_AVATAR`) → 출생 정보(400) → 만 14세(403 `UNDER_AGE`, 가입권을 지운다). 닉네임 중복(409 `NICKNAME_TAKEN`)은 마지막 트랜잭션 안에서 본다. 400 · 409 는 모두 가입권을 남긴다.
5. **푸시 수신 동의**: 가입의 `pushConsent`(선택, 기본 false) — 켜면 그때의 서버 시각, 아니면 null. `PATCH /account { pushConsent? }` 로 바꾸고, 같은 값이면 일시를 바꾸지 않는다. `GET /account` 에 `pushConsent` · `pushConsentAt`. 운영체제 알림 권한 · 기기 토큰은 이 결정에 없다(푸시 기능 계획).
6. **광고성 푸시 규칙**(지금은 발송이 없다 — 발송 계획이 코드로 지킨다): 광고성 푸시는 푸시 수신 동의(`push_consented_at`)와 마케팅 수신 동의(결정 025 의 `marketing_consented_at`)가 **둘 다** 있을 때만 보낸다. 한국 시간 21~08시에는 광고성 푸시를 보내지 않는다(그래서 야간 동의 칸이 없다). 푸시 동의만 있으면 서비스 알림만 보낸다.
7. **프로필**: 가입의 `avatar` 필수(정수 1~8), 없거나 범위 밖이면 400 `INVALID_AVATAR`. `PATCH /account { avatar? }` 로 바꾸고 `GET /account` 에 `avatar`(옛 계정은 null). 그림은 앱에 있고 서버는 번호만 둔다.
8. **감사 기록**: 가입으로 계정이 생길 때 `TERMS_AGREED`(detail `{ termsVersion, privacyVersion }` — 버전만), 푸시 동의가 바뀔 때만 `PUSH_CONSENT_CHANGED`(detail `{ consent }` — 켬/끔만). 이메일 · 닉네임은 넣지 않는다. 프로필 바꾸기는 남기지 않는다.
9. 옛 계정(약관 칸이 빈 계정)은 로그인을 막지 않는다. 다시 동의받기는 약관 개정 계획에서 한다. 탈퇴하면 이 칸들은 계정 행과 함께 지워지고 감사 기록은 남는다(결정 015).

## 근거
- 버전과 시각을 함께 남기면 "누가 어느 판에 언제 동의했나" 를 답할 수 있다. 서버 시각이라 앱이 고칠 수 없다.
- 버전을 서버 한 곳에 두면 약관을 고치는 날 한 줄만 바꾸고, 옛 판을 보고 한 가입을 서버가 거절한다.
- 400 이 가입권을 쓰지 않으면 사용자가 로그인부터 다시 하지 않는다(닉네임 400 과 같은 방식, 결정 025).
- 동의를 일시 한 칸으로 두는 것은 결정 025 의 마케팅 동의와 같은 이유다(켬/끔과 시각을 한 칸이 답한다).
- 프로필을 번호로 두면 그림을 바꿔도 서버와 DB 는 그대로다.

## 대안
- 약관 동의를 참/거짓으로만 받기 — 어느 판에 동의했는지 모른다.
- 앱이 보낸 동의 시각을 저장 — 앱의 값은 고칠 수 있다.
- 약관 버전을 환경 변수로 — 배포 환경마다 맞춰야 하고 빈 값으로 뜰 수 있다. 설정 파일 한 곳은 코드와 함께 리뷰된다.
- 야간 광고 수신 동의 칸 — 야간에 광고를 보내지 않으므로 받지 않는다(소유자).
- 프로필 사진 올리기 — 소유자가 8종 중 고르기로 정했다.

## 결과·재검토 조건
- 서버가 약관 버전 · 프로필을 필수로 받으면 옛 가입 화면은 400 이다 — 스테이징은 앱 온보딩과 같은 날 올린다.
- 약관 버전을 바꾸는 날 옛 앱의 가입이 400 `TERMS_REQUIRED` 가 된다. 약관 개정 계획에서 앱 업데이트 안내(`GET /app-config`) · 다시 동의받기와 함께 바꾼다.
- 처리방침의 수집 항목에 푸시 수신 동의 일시 · 프로필 번호를 넣을지는 소유자가 정한다.
- 푸시 발송 계획이 6번 규칙을 코드와 테스트로 지킨다.

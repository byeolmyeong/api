# 056. (1.1.0) 자세한 풀이는 결제 시작 시각 뒤부터 계정의 상품을 확인해 열고, 1.0.0 수령자 · 결제 없이 여는 계정은 표로, 산 사람은 RevenueCat 으로 가리며, 옛 앱의 새 받기는 426 이다

> 상태: 활성 · 결정일 2026-11-28 · 앱 결정 101(상품 하나 · 비소모성 · 402 · 1.0.0 수령자 5 · 결제하면 두 풀이 함께 5-1 · 결제 없이 여는 계정 5-2 · 산 계정에만 5-3 · 다시 받기 무료 6 · 웹은 결제 없음 7) · 109 의 3(1.1.0 미만 앱의 받기는 426)을 서버에서 어떻게 하는지 정한다 · **결정 029 의 4 가운데 "1.0.0 은 언제나 `true`" 와 "402 는 예약" 을 대체한다**(확인 자리 · 부르는 때 · 행을 만들지 않음은 029 그대로) · 계획 앱 저장소 `docs/plans/2026-11-27-1.1.0.md` 의 S① · 번호: 계획은 "서버 결정 052" 로 적었지만 develop 에 052(오늘의 하늘 미리 만들기)가 먼저 들어가고 053 · 055 는 같은 물결의 다른 줄, 054 는 S③ 몫이라 다음 빈 번호 056 을 쓴다(제안 — 합칠 때 메인이 바꿀 수 있다)

## 맥락
- 앱 결정 101 로 1.1.0 부터 자세한 풀이(나 탭 풀이 + 시기 풀이)는 상품 하나다. 받을 수 있는지는 서버가 정하고, 없으면 402 `PURCHASE_REQUIRED` — 앱은 402 를 받으면 결제 시트를 연다(101 의 4).
- 확인 자리(`report.EntitlementPolicy.allows`)는 029 의 4 로 이미 있다: 풀이를 **새로 시작할 때만**(이미 완성 · 쓰는 중이면 그 전에 돌아간다), 생성 한도를 세기 전에 부르고, 거절이면 행을 만들지 않는다. 지금은 늘 `true` 다.
- 1.0.0 에서 하나라도 받은 계정은 상품을 가진 것으로 본다(101 의 5). 그런데 풀이 행(`detail_reports`)은 출생 정보를 바꾸면 다른 차트 것이 지워지고(결정 041), 만든 때 칸이 없다(`started_at` 은 다시 만들 때 바뀐다) → 행으로는 수령자를 끝까지 가릴 수 없다.
- 서버 main 은 앱 1.1.0 출시보다 먼저 운영에 간다(계획 "출시 순서" 2 → 5). 그 사이 1.0.0 앱은 계속 무료여야 하고, 결제는 출시일에 켜져야 한다.
- 1.0.0 앱은 결제를 모른다. 402 를 받으면 일반 오류로 보인다. 426 `UPDATE_REQUIRED` 는 받으면 업데이트 필요 화면(앱 17-1)을 띄운다(109 의 3).
- 배포는 블루 · 그린이라 새 jar 가 뜬 뒤에도 옛 jar 가 몇 분(최대 약 8분) 같은 DB 로 요청을 받는다(결정 046).

## 결정
1. **결제 시작 시각**: 설정 `byeolmyeong.purchase.starts-at`(환경 변수 `PURCHASE_STARTS_AT`, 오프셋이 붙은 ISO-8601 — 예 `2026-12-10T00:00:00+09:00`). 비어 있거나 아직 오지 않았으면 1.0.0 처럼 **모두 허용**하고 426 도 없다. 읽을 수 없는 값이면 서버가 시작하지 않는다(배포의 상태 확인에서 바로 드러나게). 출시일에 소유자 승인 뒤 값을 넣고 다시 배포한다(블루그린).
2. **표 둘(마이그레이션 하나)**:
   - `entitlements(account_id → accounts cascade, source LEGACY · STORE, created_at)`, `(account_id, source)` 가 키. 계정마다 출처별 한 줄. 출생 정보와 상관없는 계정의 것이라 출생 정보를 바꿔도 남는다 → **다시 받기는 무료**(101 의 6, 남용은 지금의 생성 한도).
   - `entitlement_allowlist(id, email 유일, created_at, created_by → admin_accounts)` — 결제 없이 여는 계정(101 의 5-2).
3. **판정**(`EntitlementPolicy.allows` — 새로 시작할 때만, 생성 한도 전, 029 의 자리 그대로). 차례대로 처음 맞는 것:
   1. 결제 시작 시각이 없거나 아직 → 허용.
   2. 계정 이메일(`accounts.email`)이 결제 없이 여는 목록에 있다 → 허용. 대소문자는 가리지 않는다(목록은 소문자로 둔다). 애플 "이메일 가리기" 계정은 가려진 주소 그대로 넣는다. 매번 표를 본다(빼면 바로 닫힌다). `entitlements` 에 적지 않는다.
   3. `entitlements` 에 그 계정의 줄이 있다(출처 무관) → 허용. 산 사람의 이후 판정은 표만 본다.
   4. RevenueCat 에 묻는다(아래 4). 상품이 있으면 `STORE` 로 적고 허용(새 기기 복원 등 — 앱의 확인 요청보다 먼저 받기를 누른 경우).
   5. 아니면 거절 → 402 `PURCHASE_REQUIRED`, 행을 만들지 않는다.
   - 상품은 하나라 `kind`(나 탭 · 시기)를 가리지 않는다.
4. **RevenueCat 확인**: REST v1 `GET https://api.revenuecat.com/v1/subscribers/{app_user_id}`(공식 문서 "Customers"), 머리 `Authorization: Bearer <비밀 키>`. 앱의 RevenueCat 사용자 id = 서버 계정 id(UUID 글자). 응답의 `subscriber.entitlements` 에 상품 이름(설정 `byeolmyeong.purchase.revenuecat-entitlement`, 기본 `detail` — 제안)이 있고 `expires_date` 가 `null`(평생 — 비소모성) 이거나 지금보다 뒤면 "있음". 이 사전은 지난 것도 담으므로 날짜를 본다.
   - 비밀 키는 환경 변수 `REVENUECAT_SECRET_KEY` 에만 둔다. 로그 · 문서에 값을 적지 않는다.
   - 결과는 계정마다 **1분** 서버 메모리에 둔다(안 산 사람이 여러 번 눌러도 한 번 묻는다). 성공한 답만 둔다. 서버를 바꾸면 비워진다(괜찮다 — 다시 물으면 된다).
   - **실패하면 허용하지 않는다**: 비밀 키 없음 · 연결 실패 · 시간 초과(연결 3초 · 읽기 5초) · 2xx 가 아님 · 읽을 수 없는 본문이면 503 `PURCHASE_CHECK_FAILED`(제안 — 돈을 받지 않고 열어 주지 않게, 그리고 산 사람에게 "사세요" 를 보이지 않게). 다시 시도하지 않는다. 행을 만들지 않는다. 로그는 사유 코드만(`event=purchase_check_failed reason=…`).
   - 이 부름은 RevenueCat 에 고객이 없으면 만든다(201). 같은 계정 id 라 앱이 나중에 쓰는 고객과 같다.
5. **옛 앱의 새 받기는 426**(109 의 3): 결제 시작 시각 뒤, 풀이를 **새로 시작할 때만**(이미 완성 · 쓰는 중이면 지금처럼 그 상태), 요청에 `X-App-Version` 이 있고 읽을 수 있으며 **1.1.0 보다 낮으면** 426 `{ "error": "UPDATE_REQUIRED" }` — 상품이 있어도(402 · 503 보다 먼저). 머리가 없는 요청(웹)과 읽을 수 없는 버전은 막지 않는다(앱 전체 막기 `AppUpdateInterceptor` 와 같은 읽기 — `web.parseAppVersion`). 앱 전체 막기와 따로, 받기 경로에만 있다. 이미 받은 풀이 보기 · 다른 기능은 그대로다.
6. **1.0.0 수령자(`LEGACY`)**: 결제 시작 시각 전까지, 
   - 서버가 뜰 때와 매시 10분에 채운다: `detail_reports` 의 `DONE` 행의 계정 ∪ 감사 기록 `REPORT_REQUESTED`(행위자 사용자, `detail.kind` 가 `ME` · `TIMING`, 1년 보관)의 계정 → `LEGACY`(있으면 그대로). 마이그레이션이 아니라 서버가 채우는 까닭: 첫 배포 때 마이그레이션 뒤에도 옛 jar 가 몇 분 받은 요청(감사 기록은 남는다)을 다음 번이 따라 적는다. 두 서버가 함께 돌아도 같은 결과다(있으면 그대로) — 일정 잠금이 필요 없다.
   - 나 탭 풀이 · 시기 풀이가 완성될 때마다(`MeReportDone` · `TimingReportDone`) 그 계정에 `LEGACY` 를 더한다. 이 기록이 실패해도 완성 알림(알림함 · 푸시)은 그대로 간다.
   - 결제 시작 시각부터는 둘 다 멈춘다. 그 뒤의 무료 받기는 없다.
   - 수령자는 둘 중 하나만 받았어도 둘 다 열린다(101 의 5 — 판정이 `kind` 를 보지 않는다).
7. **결제 직후 확인** `POST /entitlements/confirm`(세션, 본문 없음 — 제안): 앱이 결제 · 복원 직후 부른다. RevenueCat 을 **캐시 없이** 묻고(실패면 503), 있으면 `STORE` 로 적은 뒤 **나 탭 풀이와 시기 풀이를 함께 시작**한다(101 의 5-1 — 받기 경로와 같은 길이라 이미 완성 · 쓰는 중이면 그대로) → 200 `{ detail: true, me, timing }`(각 풀이의 상태). 없으면 200 `{ detail: false }`(앱은 "복원할 구매가 없어요"). 결제 없이 여는 계정 · `LEGACY` 도 스토어 구매가 없으면 `false` 다(복원은 스토어 구매만). 다시 불러도 같다(멱등) — 적은 뒤 시작에서 404 `NO_PROFILE` · 429 `RATE_LIMITED` 가 나면 그 답이 가지만 구매는 적혀 있고, 다시 부르면 남은 풀이를 시작한다. 다른 탭의 완성 알림은 지금 알림 그대로다.
8. **"샀음" 읽기** `GET /entitlements`(세션 — 제안) → `{ detail: boolean }` = 3 의 판정과 같은 값(결제 시작 전이면 모두 `true`, RevenueCat 실패면 503). 앱은 이 값으로 화면만 바꾸고, 받기 가능 판정은 여전히 402 다.
9. **결제 없이 여는 계정 관리**: `GET · POST · DELETE /admin/entitlement-allowlist`(관리자, 제안) — 어드민 D② 가 쓴다. 추가 · 삭제는 감사 기록(이메일은 넣지 않는다 — id 만).
10. **웹**: 결제하지 않는다(101 의 7). 웹의 받기도 같은 판정이라 안 산 계정은 402(웹 앱은 "앱에서 받기" 안내), 산 계정 · 수령자는 웹에서도 받는다. 426 은 웹에 가지 않는다.
11. **그대로인 것 · 넣지 않는 것**: 궁합 · 오늘의 하늘 · 별명에는 확인이 없다(104 의 5). 가격은 서버에 적지 않는다(스토어가 정한다). 관리자의 다시 만들기(`POST /admin/users/{id}/regenerate`)도 같은 길이라 402 · 503 이 관리자에게 그대로 간다(426 은 버전 머리가 없어 없다). 환불되면 상품을 거둘지(RevenueCat 웹훅)는 101 의 [확인 필요]가 닫힌 뒤 — 지금은 `STORE` 줄이 남는다. 계정을 지우면 줄도 지워진다(다른 소셜로 새로 들어온 계정은 산 게 없는 사람이다 — 101 의 5-3).
12. **옛 심층 리포트(`POST /reports`)도 같은 판정**: 앱(main · develop)은 부르지 않지만 경로가 열려 있어, 결제 시작 뒤 안 산 계정이 이 길로 받지 못하게 새로 시작할 때 5(426) → 3(402 · 503)을 같은 차례로 거친다. 이 경로의 받기는 1.0.0 수령자로 치지 않는다(앱이 부르지 않는 옛 경로). 경로 지우기는 계획 S⑤ 정리 몫이다.

## 근거
- 결제 시작을 설정 하나로 두면 서버 main 을 먼저 올려도 1.0.0 사용자는 그대로 무료이고, 출시일에 값 하나로 켜고(블루그린 10초) 문제가 있으면 비워서 끈다.
- 수령자를 계정의 표에 적으면 출생 정보를 바꿔도, 감사 기록이 1년 뒤 지워져도 남는다. 출처를 함께 적어 나중에 "산 사람" 과 "1.0.0 수령자" 를 나눠 셀 수 있다.
- 산 사람을 적어 두면 이후 판정에서 RevenueCat 을 부르지 않는다(받기 · "샀음" 읽기가 외부 장애에 덜 묶인다). 표에 없을 때만 묻고 1분 담아 두면 안 산 사람이 눌러도 부름이 늘지 않는다.
- RevenueCat 이 안 될 때 열어 주면 돈 없이 열리고, 402 를 주면 이미 산 사람에게 결제 시트가 뜬다 → 503 이 둘 다 피한다.
- 426 을 받기에만 주면 이미 받은 1.0.0 사용자는 옛 앱을 그대로 쓰고, 옛 앱으로 유료를 피해 가는 길만 막힌다(109).
- 확인 요청이 두 풀이를 함께 시작하면 "상품 하나 · 풀이 둘" 에서 한쪽만 제공을 시작한 상태가 생기지 않는다(101 의 5-1, 청약철회).

## 대안
- 풀이 행(`detail_reports`)으로 수령자를 가리기 — 출생 정보를 바꾸면 지워지고 만든 때를 몰라 결제 시작 뒤에 받은 것과 섞인다.
- 배포 때 한 번만 채우기(마이그레이션) — 첫 배포의 블루그린 겹침 동안 옛 jar 가 받은 요청을 놓친다.
- RevenueCat 실패 때 허용 · 402 — 위 "근거".
- 웹훅만으로 구매를 받기 — 웹훅이 늦거나 빠지면 산 사람이 바로 못 받는다. 확인 요청 + 표에 없을 때 조회가 더 단순하다. 웹훅은 환불 회수 때 다시 본다.
- 1.0.0 앱 전체를 최소 버전으로 막기 — 이미 받은 사람까지 막는다(109 의 대안).
- `GET /entitlements` 를 결제 시작 전에도 실제 구매로 답하기 — 결제 시작 전에는 모두 받을 수 있어 화면과 판정이 어긋나고, RevenueCat 키가 없는 스테이징에서 503 이 난다.

## 결과·재검토 조건
- 계약: docs/architecture.md 의 `POST /me-report` · `POST /timing-report`(402 실제 · 426 · 503), `GET /entitlements` · `POST /entitlements/confirm`, "결제 없이 여는 계정"(관리자 API), 감사 행동 `ENTITLEMENT_ALLOWLIST_ADDED` · `ENTITLEMENT_ALLOWLIST_REMOVED`, 데이터 · 외부 시스템 절. 앱(A③ 결제 시트 · 복원, 1.1.0 의 426 처리)과 어드민(D②)에 맞춤 변경이 필요하다.
- 설정: `PURCHASE_STARTS_AT` · `REVENUECAT_SECRET_KEY`(이름만 `.env.example` · `deploy/.env.example`). 스테이징에서 실제 구매를 확인하려면 RevenueCat 계정 · 스토어 상품 · 키가 있어야 한다(소유자 준비) — 그전에는 가짜 클라이언트 테스트로 합친다.
- [확인 필요] RevenueCat 상품(entitlement) 이름 — 기본 `detail`. 다르면 설정만 바꾼다.
- [확인 필요] 환불 회수(웹훅)와 RevenueCat 복원 동작("처음 산 사용자에게") — 101.
- RevenueCat 장애로 503 이 잦으면(로그 `event=purchase_check_failed`) 시간 · 캐시를 다시 본다.
- 결제 없이 여는 목록이 커지거나 이메일이 바뀌는 계정이 생기면(공급자가 주는 이메일은 가입 때 값) 계정 id 로 고르는 길을 다시 본다.

# 047. 웹 클라이언트가 받은 구글 ID 토큰은 만료까지 한 번만 받는다(jti)

> 상태: 활성 · 결정일 2026-11-20(앱 세션 fa 의 보안 요청 — 앱 결정 070 · 앱 PR #58 의 리뷰, 운영 전 필요) · 결정 021(소셜 로그인)에 더한다 · 계약 변화 없음 · 두 서버가 함께 뜨는 배포(결정 046)

## 맥락
- 앱 웹의 구글 로그인이 GIS 겹치기에서 OpenID Connect 리디렉트(`response_type=id_token` · nonce · state, 앱 결정 070)로 바뀐다. 돌아오는 주소 조각(`#id_token=…`)의 ID 토큰은 **브라우저 방문 기록에 남는다.**
- 서버(`auth.ProviderToken`)는 서명 · 발급자 · 대상 · 만료 · azp 만 보고 같은 토큰을 다시 받아도 막지 않는다. 그래서 기록에서 꺼낸 토큰으로 만료(최대 1시간)까지 `POST /auth/login` 이 다시 된다 — 같은 기기를 쓰는 다른 사람이 로그인할 수 있다.
- iOS · 안드로이드 SDK 는 저장해 둔 같은 토큰을 다시 줄 수 있어(만료 전 재사용), 그쪽까지 막으면 정상 로그인이 깨진다. 카카오 웹은 서버가 코드를 바꿔 토큰을 받으므로 기록에 남지 않는다. 애플 웹은 `form_post` 라 주소에 없다.

## 결정
1. **대상**: 구글 ID 토큰 가운데 **웹 클라이언트가 받은 것**만 — 발급받은 쪽(`azp`, 없으면 대상 `aud`)이 설정 `byeolmyeong.auth.google.web-client-id`(환경 변수 `GOOGLE_WEB_CLIENT_ID`, 비밀 아님 — `GOOGLE_CLIENT_IDS` 안의 하나)와 같을 때. iOS · 안드로이드(다른 클라이언트 ID) · 애플 · 카카오는 지금과 같다.
2. **한 번만**: 그 토큰의 `jti` 를 표 `used_id_tokens(jti 기본 키, expires_at)` 에 `insert … on conflict do nothing` 으로 선점한다. 이미 있으면 401 `INVALID_ID_TOKEN`(지금 코드 그대로 — 앱은 다시 로그인한다). `jti` 나 만료가 없는 웹 토큰도 401. 서명 · 대상 · 만료를 다 확인한 **뒤에** 선점한다(틀린 토큰이 줄을 만들지 않게).
3. **공유 저장**: 서버 메모리가 아니라 DB 다 — 배포 중 두 서버가 함께 떠도(결정 046) 한 번이다. 줄은 토큰이 끝나는 때(`exp`)까지만 뜻이 있고, 날마다 한국 시각 04:15 에 지난 줄을 지운다(같은 지우기라 두 서버가 함께 돌아도 결과가 같다).
4. **설정이 비면** 검사를 끄고 시작할 때 경고 로그(`event=id_token_once_off`)를 남긴다 — 로컬 · 테스트. 운영 · 스테이징 `.env` 에는 웹 클라이언트 ID 를 넣는다.
5. 로그에는 토큰 · `jti` 원문을 남기지 않는다(`event=id_token_replayed` 만).

## 근거
- `jti` 는 구글이 토큰마다 주는 고유 값이라, 같은 토큰을 다시 보냈는지 정확히 가린다. 만료까지만 기억하면 되므로 표가 커지지 않는다.
- 웹만 거는 것은 기록에 남는 길이 웹 리디렉트뿐이고, SDK 의 저장본 재사용을 깨지 않기 위해서다.

## 대안
- 모든 구글 토큰에 걸기 — SDK 가 같은 토큰을 다시 줄 때 정상 로그인이 401 이 된다.
- nonce 를 서버가 발급하고 한 번만 받기 — 서버에 로그인 전 상태가 하나 더 생기고 앱 흐름(앱 결정 070)이 바뀐다. jti 한 번만으로 다시 쓰기는 막힌다.
- 서버 메모리에 기억 — 배포 중 두 서버 · 재시작에 뚫린다.

## 결과·재검토 조건
- 앱 결정 070 의 운영 조건("서버 047")이 이 결정이다. 앱 main 승격은 이 결정이 운영에 나간 뒤.
- 운영 · 스테이징 `.env` 에 `GOOGLE_WEB_CLIENT_ID` 를 넣는다(배포 담당).
- 웹 클라이언트 ID 가 바뀌면 설정만 바꾼다.

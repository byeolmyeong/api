# 서버 아키텍처

> 상태: 활성 · 기준 2026-11-10 · 구현 전 설계다. 전체 구성과 비즈니스 룰의 원본은 앱 저장소의 `../byeolmyeong-app/docs/architecture.md` 다.

## 서버가 하는 일
- 익명 계정 발급: 기기마다 계정과 토큰을 준다. 로그인 화면은 없다. 이유: 가입 장벽이 첫 화면 이탈을 만든다.
- 해석 생성·저장: 앱이 보낸 차트 JSON 으로 OpenAI API 를 호출해 해석을 만들고 저장한다. 같은 소유자·차트·종류는 저장본을 돌려준다. 이유: 같은 차트의 해석이 볼 때마다 달라지면 신뢰가 깨지고 재생성은 비용이다.
- 공유 조회: 추측할 수 없는 공유 식별자로 요약 해석 본문만 내보낸다. 출생 정보는 내보내지 않는다.
- 구매 확인(보류): 결제를 붙일 때 추가한다.

## 서버가 하지 않는 일
- 차트 계산. 앱의 계산 엔진이 한다. 서버는 형식과 값 범위(천체 10개, 황경 0 이상 360 미만)만 검사한다. 이유: 계산 코드를 두 언어로 두면 결과가 어긋난다.

## API 계약 (앱 저장소와 맞춘다)
| 메서드·경로 | 인증 | 요청 | 응답 |
|---|---|---|---|
| `POST /accounts` | 없음 | 없음 | `{ token }` |
| `POST /readings` | 토큰 | `{ kind: SUMMARY\|DEEP\|SYNASTRY, chart, partnerChart? }` | `{ sections: [{ title, body, basis[] }], shareId }` |
| `GET /shared/{shareId}` | 없음 | 없음 | `{ sections }` (요약 해석만) |

## 데이터
- `accounts` — 익명 계정. 토큰은 해시로 저장한다.
- `readings` — 소유자, 종류, 차트 해시, 본문 JSON, 공유 식별자(unique). (소유자, 차트 해시, 종류) unique. 이유: 동시 요청이 와도 해석은 하나만 남는다.

## 해석 생성 규칙
- 프롬프트는 리소스 파일로 둔다. 본문에 점성술 용어를 쓰지 않고, 문단마다 근거(차트 요소)를 별도 필드로 받는다. 건강·투자·미래 사건을 단정하지 않는다. 근거: 앱 저장소 `docs/product.md` 컨셉.
- 출생 시각을 모르는 차트(`timeKnown: false`)에는 하우스·상승궁 기반 문장을 요구하지 않는다.
- 생성 호출부는 인터페이스 하나 뒤에 둔다. 이유: 공급자(OpenAI)와 모델을 바꿀 수 있어야 한다.
